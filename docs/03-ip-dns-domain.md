# 第3章 IPアドレス・ドメイン・DNS — 住所と電話帳

> **この章でわかること**
> - IPアドレスが何をしているのかを説明できる
> - ドメイン名とIPアドレスの関係、DNSが果たす役割を説明できる
> - `example.com` と打つだけで目的のサーバーに届く仕組みを説明できる
> - DNSの変更がすぐには反映されないことがある理由を説明できる
>
> **前の章とのつながり**: 前章では、EC2という「プログラムを動かす場所」を用意しました。しかし建物を建てただけでは、来客はその場所を見つけられません。この章では、インターネット上で「どこに行けばよいか」を特定する仕組みを扱います。

## なぜこれが必要なのか

ブラウザに `example.com` と入力すると、世界のどこかにあるサーバーから正しくページが返ってきます。しかし、インターネットの世界には「住所」にあたる番号の仕組みしかなく、`example.com` のような文字列そのものでは通信できません。では、人間が読みやすい文字列と、機械が使う番号は、どこでどう結びついているのでしょうか。この結びつきの仕組みを知らないと、ドメインを取得しただけではサイトが表示されない理由も、Route 53のような「AWSのDNSサービス」がなぜ必要なのかも理解できません。

## まずはざっくり: 中学生にもわかる説明

友達の家に手紙を送るとき、「田中さんの家」という呼び方だけでは郵便配達員は届けられません。実際には「東京都〇〇区〇〇1-2-3」という住所が必要です。インターネットも同じで、コンピューター同士は「住所」にあたる番号でしか相手を見つけられません。ただし人間は数字の羅列を覚えるのが苦手なので、「example.com」のような覚えやすい名前を使い、それを住所に変換する「電話帳」のような仕組みを間に挟んでいます。この電話帳の仕組みが、この章で説明するDNSです。

## 身近なたとえ

IPアドレスは「住所（番地）」、ドメインは「店の名前」、DNSは「電話帳・住所録」にあたります。私たちは「〇〇商店に行きたい」と思ったとき、店の名前だけで場所がわかるわけではなく、住所録を引いて番地を調べてから向かいます。インターネットでも、ブラウザは「example.comに行きたい」と思ったときに、まず電話帳（DNS）を引いて住所（IPアドレス）を調べ、その住所に向かって通信しています。

## 技術的にはこういうこと

**IPアドレス（Internet Protocol Address）**は、インターネットに接続された機器を識別するための番号です。`203.0.113.10` のように、数字をピリオドで区切った形式（IPv4）で表されます。最終的に、ブラウザとサーバーの間の通信はすべてこのIPアドレスを使って行われます。

IPアドレスには大きく分けて2種類があります。**パブリックIPアドレス**はインターネット上で直接やり取りできる、世界で重複しない番号です。一方**プライベートIPアドレス**は、家庭内のWi-Fiルーターの中や、AWSの中だけで使われる番号で、インターネットには直接出て行きません。`10.0.0.0` から始まる範囲や `192.168.0.0` から始まる範囲などが、プライベートIP用として予約されています。この区別は、第5章で登場するVPC（自分専用の仮想ネットワーク）を `10.0.0.0/16` というプライベートIPの範囲で構築する際の前提になりますので、ここで押さえておいてください。

**ドメイン名**は、`example.com` のように人間が読みやすい形式で表された名前です。ドメイン名自体はただの文字列で、通信の宛先そのものではありません。

**DNS（Domain Name System）**は、ドメイン名をIPアドレスに変換する仕組みです。この変換作業を「名前解決」と呼びます。DNSは1台のサーバーがすべての対応表を持っているわけではなく、階層構造になっています。

```text
        Browser
           │
           ▼
      Root Server        (「.com はどこ？」を知っている)
           │
           ▼
      TLD Server         (.com を管理する。次の行き先を知っている)
           │
           ▼
   Authoritative DNS   (example.comの実際のIPアドレスを回答)
           │
           ▼
      IP Address         (例: 203.0.113.10)
```

（TLDはTop Level Domainの略で、`.com` や `.jp` のようにドメインの一番右側にある部分を指します。Authoritative DNS（権威DNSサーバー）とは、あるドメインについて「正しい答え」を持っている、そのドメインの管理担当サーバーのことです。）

この階層をたどるたびに問い合わせをしていると時間がかかるため、一度調べた結果は一定時間**キャッシュ**（問い合わせ結果を手元に一時保存しておくこと）されます。この保存期間を**TTL（Time To Live）**と呼び、秒単位で設定されます。TTLが3600（1時間）であれば、一度名前解決した結果は1時間の間、再度問い合わせずに使い回されます。これが「DNSの設定を変更しても、すぐには反映されない」ことがある理由です。世界中のブラウザやネットワーク機器がそれぞれ古い情報をキャッシュとして持っているため、変更が行き渡るまでには時間差が生じます。

また、ブラウザとサーバーが通信する際には、IPアドレスに加えて**ポート番号**という情報も使われます。ポート番号は、同じ住所（IPアドレス）の中にある「どの窓口宛てか」を示す番号です。Webサイトの通信では、暗号化なしの通信（HTTP）はポート80、暗号化あり（HTTPS）はポート443が標準として使われます。ブラウザで `https://example.com` にアクセスすると、実際には「IPアドレス 203.0.113.10 のポート443宛て」に通信していることになります。

## AWSでの具体例

Route 53（AWSのDNSサービス。詳細は次章で扱います）でドメインを管理する場合、ホストゾーンという設定単位の中に「example.com は 203.0.113.10 である」といった対応情報（レコード）を登録します。この情報が、権威DNSサーバーとして世界に公開される内容になります。

```text
        Browser
           │
           ▼
      DNS (Route 53)     example.com ► 203.0.113.10
           │
           ▼
       IP Address
           │
           ▼
        Server           (ポート443でHTTPSを待ち受け)
```

レコードにはTTLを設定でき、値を短くしておくと変更の反映が速くなりますが、その分すべての問い合わせがキャッシュを介さず届くことになります。

## フロントエンド開発との関係

VercelにNext.jsアプリをデプロイすると、`your-app.vercel.app` のようなサブドメインが自動的に割り当てられ、すぐにアクセスできるようになります。これは、Vercel側があらかじめ用意している親ドメイン（`vercel.app`）の下にDNSレコードを自動的に追加してくれているためです。一方、そこに独自ドメイン（例えば `example.com`）を設定する場合は、ドメインの管理画面（お名前.comやRoute 53など）で「このドメインはVercelを見てください」という設定（DNSレコードの追加）を自分で行う必要があります。この設定を追加した直後にアクセスしてもまだ反映されていないことがあるのは、まさに前述のTTLによるキャッシュが原因です。「ドメインをつないだのにまだ古いサイトが見える」という経験がある方は、DNSのキャッシュが効いていたことになります。

## よくある勘違い

> **勘違い**: ドメインを取得すれば、それだけでサイトが表示される。
> **実際は**: ドメインは名前にすぎず、そのドメインとサーバーのIPアドレスを結びつけるDNSの設定（レコードの登録）が別途必要です。

> **勘違い**: DNSの設定を変更すれば、世界中で即座に反映される。
> **実際は**: TTLによるキャッシュが各所に残っているため、反映には設定したTTLの時間程度、あるいはそれ以上かかることがあります。

> **勘違い**: IPアドレスはすべてインターネットから直接アクセスできる。
> **実際は**: パブリックIPとプライベートIPの区別があり、プライベートIPは特定のネットワーク内でのみ通用し、インターネットへは直接出られません。

> **勘違い**: ポート番号は特別な場合だけ意識すればよい。
> **実際は**: `https://` でアクセスするたびに、裏側では常にポート443番宛ての通信が行われています。私たちが意識していないだけです。

## この章で覚えるべきポイント

- [ ] IPアドレスが通信の最終的な宛先であり、ドメイン名はそのための人間向けの別名であると説明できる
- [ ] DNSがドメイン名をIPアドレスに変換する「名前解決」の仕組みであると説明できる
- [ ] ルートサーバー→TLDサーバー→権威DNSサーバーという階層をたどって名前解決が行われると説明できる
- [ ] TTLによるキャッシュが、DNS変更の反映に時間差を生む理由であると説明できる
- [ ] パブリックIPとプライベートIPの違いを説明できる
- [ ] HTTPはポート80、HTTPSはポート443が標準で使われることを説明できる

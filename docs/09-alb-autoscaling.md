# 第9章 ALBとAuto Scaling — 受付係と、人手の自動増減

> **この章でわかること**
> - EC2が1台だけの構成では何が困るのかを説明できる
> - ALB（Application Load Balancer）がリクエストをどう振り分けるかを説明できる
> - Auto Scalingが台数をどう自動調整するか、ALBとどう連携するかを説明できる
> - この章を境にEC2をPublic SubnetからPrivate Subnetへ移せる理由を説明できる
>
> **前の章とのつながり**: 第8章までで、Security Groupという門番を立てた1台のEC2にPublic Subnet経由でアクセスできる状態まで来ました。この章では、そのEC2を「複数台」に増やし、リクエストを振り分ける仕組みを導入します。

## なぜこれが必要なのか

第5章から第8章までの構成では、EC2はPublic Subnetに1台だけ置かれていました。この構成には2つの弱点があります。ひとつは、そのEC2が停止するとサイト全体が止まってしまうこと（単一障害点）。もうひとつは、アクセスが増えたときに1台では処理しきれなくなることです。

では単純にEC2を2台に増やせば解決するかというと、そうはいきません。ユーザーはexample.comという1つのアドレスにアクセスするだけなので、「2台のうちどちらに振り分けるか」を判断する係が必要です。さらに、アクセス数は常に一定ではなく、時間帯によって増減します。台数を人手で毎回調整するのは現実的ではありません。「複数台に振り分ける仕組み」と「台数そのものを自動で調整する仕組み」の両方が必要になります。

## まずはざっくり: 中学生にもわかる説明

お店を1人で切り盛りしていると、お客さんが増えたときに対応しきれません。そこで、まず「受付」を置いて、来店したお客さんを空いているスタッフのところへ案内するようにします。さらに、混雑する時間帯にはスタッフを増やし、空いている時間帯には減らす店長がいれば、常に適切な人数で店を回せます。この「受付」がALB、「店長」がAuto Scalingにあたります。

## 身近なたとえ

ALBは「受付・案内係」です。お客さん（リクエスト）が来ると、今どのスタッフ（EC2）が対応可能かを見て、空いている窓口へ案内します。Auto Scalingは「混雑に応じてスタッフを増減する店長」です。忙しくなればスタッフ（EC2）を増やすよう手配し、暇になれば減らします。受付とスタッフはどちらも敷地（VPC）の中にいますが、受付は表の区画（Public Subnet）に立って外からのお客さんを迎え、スタッフ自身は奥の区画（Private Subnet）で働くことができます。

## 技術的にはこういうこと

ALB（Application Load Balancer）は、HTTP/HTTPSといったアプリケーション層（レイヤー7）の通信を複数のEC2インスタンスへ振り分けるロードバランサーです。ALBには次の3つの要素が登場します。

- **リスナー（Listener）**: ALBがどのポート・プロトコル（例: 80番でHTTP、443番でHTTPS）で通信を受け付けるかの設定です。
- **ターゲットグループ（Target Group）**: 振り分け先となるEC2インスタンスの集まりです。ALBはリクエストをターゲットグループ内のインスタンスに分配します。
- **ヘルスチェック（Health Check）**: ターゲットグループ内の各EC2に対して、ALBが定期的に「正常に応答するか」を確認する仕組みです。応答がないEC2は振り分け先から自動的に外され、復旧すれば自動的に戻されます。

ここで重要なのは、**ALB自身が台数を増減させるわけではない**という点です。台数の管理を担うのはAuto Scaling Group（ASG）です。ASGは「最小台数・希望台数・最大台数」といった条件と、CPU使用率などの指標に基づくスケーリングポリシーを持ち、条件に応じてEC2インスタンスを起動・終了します。ASGが新しいEC2を起動すると、そのインスタンスは自動的にALBのターゲットグループに登録され、ヘルスチェックを通過した時点から振り分け対象に加わります。つまり「ALBが振り分け、ASGが台数を管理し、両者はターゲットグループを介してつながっている」という2段構えの仕組みです。

このAuto Scalingは**水平スケーリング**（台数を増やす）であり、1台のスペックを上げる**垂直スケーリング**（例: EC2のインスタンスタイプをより高性能なものに変更する）とは区別されます。垂直スケーリングには上限があり、また変更時にインスタンスの再起動が必要になることが多いのに対し、水平スケーリングは台数を増減するだけなので、稼働させたまま柔軟に対応しやすいという特徴があります。

ここで3つの用語を整理します。**可用性（Availability）**とは、システムが停止せずに使える状態をどれだけ維持できるかを指します。1台のEC2が壊れても他のEC2が応答を続けられれば可用性が高いといえます。**スケーラビリティ（Scalability）**とは、負荷の増減に応じて処理能力を調整できる度合いを指します。**冗長化（Redundancy）**とは、同じ役割を持つ構成要素を複数用意しておき、一部が壊れても全体が止まらないようにしておくことです。ALBとAuto Scalingを組み合わせたEC2複数台構成は、この3つすべてを底上げする仕組みです。

なお、ALBは1つのAZ（Availability Zone。第5章で触れた「Subnetは1つのAZに属する」という区分の単位）のSubnetだけでは動作せず、**異なる2つ以上のAZにまたがるSubnetを指定する必要があります**。これは、AZ自体が丸ごと利用できなくなった場合でも受付機能を止めないための仕組みです。本章の図は説明のためにAZを省略した簡略図であり、実運用では複数AZでの構成が前提になります（AZの詳細は第17章で扱います）。

ALBを導入すると、EC2への直接アクセスはALB経由に一本化できます。これにより、EC2はPublic Subnetに置いて自らインターネットと直接やり取りする必要がなくなり、**Private Subnetへ移すことができます**。EC2のSecurity Group（門番。本書では `app-sg` と呼びます）は、それまで許可していた「インターネットからの80番」ではなく、「**ALBのSecurity Group（`alb-sg`）からの80番のみ許可**」に変更します。外部からの通信は必ずALBを経由し、EC2自体はインターネットから直接見えない状態になります。

```text
        User (Browser)
              │
              ▼
         Route 53
              │
              ▼
            ALB                        ◄── ここが本章の主題
      (Listener: 80/443)
      (Target Group + Health Check)
         ┌────┴────┐
         ▼         ▼
       EC2        EC2                  ◄── ここが本章の主題
      (Auto Scaling Groupが台数管理)
```

ALBはPublic Subnetの2つ以上のAZに配置し、EC2はPrivate Subnetへ移動しています。

```text
            Internet
               │
               ▼
      ┌─── Internet Gateway ───┐
      │                        │
┌─────┴────────── VPC ─────────┴─────┐
│ 10.0.0.0/16                        │
│                                    │
│  ┌─── Public Subnet 10.0.1.0/24 ─┐ │
│  │   ALB                         │ │  ◄── ここが本章の主題
│  │   NAT Gateway                 │ │
│  └───────────────────────────────┘ │
│                 │                  │
│                 ▼                  │
│  ┌─── Private Subnet 10.0.2.0/24 ┐ │
│  │   EC2  (App / Auto Scaling)   │ │  ◄── ここが本章の主題
│  │   RDS  (Database)             │ │
│  └───────────────────────────────┘ │
│                                    │
└────────────────────────────────────┘
```

ALBは2つ以上のAZのSubnetにまたがって配置する必要があります（本図は簡略図）。EC2はAuto Scaling Groupの管理下でPrivate Subnetに置かれます。

## AWSでの具体例

実際にAWSでこの構成を組む場合は、次のような設定を行います。

- EC2 コンソールで**ターゲットグループ**を作成し、プロトコルとポート（例: HTTP / 80）を指定する。
- **Application Load Balancer**を作成し、Public Subnetのうち2つ以上のAZにまたがるSubnetを選択する。
- ALBの**リスナー**に80番（必要に応じて443番）を設定し、転送先として先ほどのターゲットグループを指定する。
- ターゲットグループに**ヘルスチェックパス**（例: `/health`）を設定し、正常応答の判定条件を決める。
- **起動テンプレート（Launch Template）**でEC2の設定（AMI、インスタンスタイプ、Security Group）を定義し、それを使う**Auto Scaling Group**を作成する。
- Auto Scaling Groupに「最小1台・希望2台・最大5台」のような台数条件と、CPU使用率などに基づくスケーリングポリシーを設定する。
- Auto Scaling GroupにALBのターゲットグループを関連付け、起動したEC2が自動的に登録されるようにする。
- EC2のSecurity Group（`app-sg`）のインバウンドルールを、ALBのSecurity Group（`alb-sg`）からの80番のみ許可に変更する。

## フロントエンド開発との関係

Vercel・NetlifyでNext.jsのサーバーレス関数やSSRページをデプロイすると、アクセス集中時に自動的にスケールしてくれます。利用者は「今何台の実行環境が動いているか」を意識する必要がありません。AWSでALBとAuto Scalingを自分で構成するということは、Vercel/Netlifyが裏側で自動的にやっていた「振り分け」と「台数調整」を、自分でターゲットグループやスケーリングポリシーとして明示的に設定する作業に相当します。自由度が上がる一方、ヘルスチェックの設計やスケーリング条件のチューニングは自分の責任になります。

## よくある勘違い

> **勘違い**: ALBがEC2の台数を増やしたり減らしたりしている。
> **実際は**: 台数を管理するのはAuto Scaling Groupです。ALBは振り分けとヘルスチェックのみを担当し、ASGが起動したEC2をターゲットグループに登録することで両者がつながります。

> **勘違い**: Auto Scalingは1台のスペックを上げる仕組みである。
> **実際は**: Auto Scalingは台数を増減させる水平スケーリングです。スペックを上げる垂直スケーリングとは別の仕組みです。

> **勘違い**: ALBは1つのSubnetに置けば動作する。
> **実際は**: ALBは異なる2つ以上のAZのSubnetを指定する必要があります。1つのAZが利用できなくなっても受付機能を止めないためです。

> **勘違い**: EC2をPrivate Subnetに移すと、ユーザーはサイトにアクセスできなくなる。
> **実際は**: ユーザーからのリクエストは常にALB（Public Subnet）を経由するため、EC2自体がPrivate Subnetにあってもアクセスは成立します（EC2のSecurity Group `app-sg` はALBのSecurity Group `alb-sg` からの通信のみ許可）。EC2への直接アクセスができなくなるだけです。

> **勘違い**: ヘルスチェックに失敗したEC2は、二度と振り分け対象に戻らない。
> **実際は**: ヘルスチェックは継続的に行われるため、EC2が復旧して正常応答するようになれば、再びターゲットグループの振り分け対象に戻ります。

## この章で覚えるべきポイント

- [ ] ALBはL7（HTTP/HTTPS）のロードバランサーであり、リスナー・ターゲットグループ・ヘルスチェックの3要素を持つ
- [ ] ALB自身は台数を増減させず、台数管理はAuto Scaling Groupが担う
- [ ] Auto Scalingは水平スケーリング（台数増減）であり、垂直スケーリング（スペック向上）とは区別される
- [ ] ALBは2つ以上のAZのSubnetが必要である
- [ ] ALB導入後、EC2はPrivate Subnetへ移し、EC2のSecurity Group（`app-sg`）はALBのSecurity Group（`alb-sg`）からの通信のみを許可する
- [ ] 「可用性」「スケーラビリティ」「冗長化」の意味を説明できる

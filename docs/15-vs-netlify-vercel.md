# 第15章 Netlify / Vercel は何を代わりにやってくれていたのか

> **この章でわかること**
> - Netlify / Vercel が隠蔽している機能と、AWSでの対応部品を機能軸で対応づけられる
> - 同じサイトをAWSで組むと部品が何個必要になるかを数えられる
> - 「自由度は高いが知識が必要」を、責任範囲の違いとして説明できる
> - 用途に応じてNetlify / Vercel と AWS を使い分ける判断基準を示せる
>
> **前の章とのつながり**: [第13章](./13-architecture-static.md)と[第14章](./14-architecture-server.md)で、2つの構成を最後まで組み立てました。この章では、それを普段使っているプラットフォームと並べて比べます。

## なぜこれが必要なのか

ここまで読み進めた方は、途中で一度こう思ったはずです。「Netlifyなら数クリックで終わる話なのに、なぜこんなに部品が必要なのか」。

その感覚は正しく、そして重要です。Netlify や Vercel が数クリックで済ませてくれていたのは、**やらなくてよかったから**ではなく、**誰かが代わりにやっていたから**です。この章では、その中身をこれまで学んだAWSの部品名で1つずつ言い当てていきます。これができると、障害や制約に出会ったときに「どの層で何が起きているのか」を推測でき、プロジェクトごとの選択にも根拠を持てるようになります。

## まずはざっくり: 中学生にもわかる説明

店を開くときの2つの始め方にたとえると分かりやすくなります。

Netlify や Vercel は、**すでに建物も受付も倉庫も配送網も整った施設の一区画を借りる**やり方です。契約したその日から、荷物を持ち込むだけで営業を始められます。その代わり、区画の間取りを変えたり、施設の配送のしかたを自分で決めたりすることはできません。

AWSは、**国の中に自分の土地を借り、区画を切り、正門を建て、門番を雇い、建物や倉庫を建てる**やり方です。何をどこに置くかも、誰を通すかも自分で決められます。その代わり、決めなかったものはそのまま存在しないままになります。門を建てなければ人は入ってこられず、門番を置かなければ誰が入ってよいかも決まりません。

どちらが優れているという話ではありません。荷物を置いて配るだけなら施設を借りるほうが合理的ですし、奥まった場所に金庫室を構えるような特別な要件があるなら、自分で土地から用意するしかありません。**選ぶ基準は「何が必要か」であって、「どちらが上か」ではありません。**

## 身近なたとえ

前章までの世界観で言い直すと、こうなります。

Netlify や Vercel を使うのは、**すでに建物も受付も配送網も整った施設の一区画を借りる**ことです。倉庫も各地の前線倉庫も住所録への登録も、すべて施設の運営会社がやってくれます。利用者は荷物を持ち込むだけです。

AWSを使うのは、**国の中に自分の土地を借り、区画を切り、正門を建て、門番を雇い、倉庫を建てる**ことです。運営会社の代わりに自分が設計者になります。同じ「荷物を届ける」結果に到達しますが、途中でどれだけの判断を自分でするかが違います。

## 技術的にはこういうこと

機能軸で並べると、対応関係は次のようになります。

| 機能 | Netlify / Vercel | AWSでの部品（章） |
|---|---|---|
| ソースからのビルド | Gitに繋げば自動でビルド | GitHub Actions等のCIで `astro build` を実行（[第13章](./13-architecture-static.md)） |
| 成果物の配置先 | publish directory を指定するだけ | S3バケット（[第11章](./11-s3-ssg.md)） |
| CDN配信 | Vercel Edge Network / Netlify CDN が標準で有効 | CloudFront（[第12章](./12-cloudfront.md)） |
| HTTPS証明書 | ドメインを登録すると自動で発行・更新 | ACM（CloudFront用はus-east-1で発行。[第12章](./12-cloudfront.md)） |
| DNS | ダッシュボードでドメインを追加 | Route 53のホストゾーンとAliasレコード（[第4章](./04-route53.md)） |
| キャッシュ管理 | デプロイのたびに自動でパージ | CloudFrontのTTL設計とInvalidation（[第12章](./12-cloudfront.md)） |
| サーバー実行環境 | サーバーレス関数が自動で用意される | EC2（[第2章](./02-ec2.md)） |
| 負荷分散 | 意識しない | ALBのリスナー・ターゲットグループ・ヘルスチェック（[第9章](./09-alb-autoscaling.md)） |
| スケーリング | 自動 | Auto Scaling Group（[第9章](./09-alb-autoscaling.md)） |
| データベース | 別サービスに接続文字列で接続 | RDS（[第10章](./10-rds.md)） |
| ネットワーク分離 | 利用者からは見えない | VPC / Subnet（[第5章](./05-vpc-subnet.md)） |
| 外部との接続経路 | 意識しない | Internet Gateway / Route Table / NAT Gateway（[第6章](./06-igw-routetable.md)・[第7章](./07-nat-gateway.md)） |
| 通信の許可設定 | 意識しない | Security Group（[第8章](./08-security-group.md)） |
| インフラ管理 | 運営会社が実施 | 自分で設計・構築・監視 |

**部品を数えてみる。**
静的サイトを1本公開する場合、必要な部品は次のとおりです。

```text
   Static site on AWS

   Route 53   (DNS + Alias record)
   CloudFront (CDN + HTTPS terminate + cache)
   ACM        (certificate, us-east-1)
   S3         (bucket, private + OAC)
   CI         (build and deploy pipeline)
```

同じことを、Netlify や Vercel では「リポジトリを繋いでビルドコマンドを指定する」1つの操作で終えられます。**5対1**です。サーバーアプリケーションの場合は、ここにさらに部品が積み上がります。

```text
   Server app on AWS (in addition to the above)

   VPC              Subnet (public x2, private x2)
   Internet Gateway Route Table (public, private)
   NAT Gateway      Security Group (alb-sg, app-sg, db-sg)
   ALB              Target Group + Health Check
   EC2              Auto Scaling Group + Launch Template
   RDS              DB Subnet Group
```

数え方にもよりますが、おおよそ**14種類前後**の構成要素を自分で設計・作成し、それらの関係を正しく設定する必要があります。

**この差は何なのか。**
重要なのは、この差が「AWSが不便だから」生じているのではない点です。上の表の右列は、**Netlify や Vercel の内部でも誰かが同じ設計をしている**ものです。多くのプラットフォームは基盤としてクラウド（AWSを含む）を使っており、利用者が触らずに済んでいるだけで消えてなくなっているわけではありません。差の正体は**責任範囲の境界線がどこに引かれているか**です。

- **ネットワークの責任**: プラットフォームでは、どのサーバーがどのネットワークにいて何と通信できるかを利用者が決められません。AWSではVPCのCIDRからSubnetの分割、Route Tableの1行までを自分で決めます。決めなければ通信は成立しません。
- **セキュリティの責任**: AWSでは `db-sg` のインバウンドに何を書くかが、そのままアクセス可能範囲になります。書き忘れれば繋がらず、広く書きすぎれば穴になります。
- **インフラ設計の責任**: 可用性（障害が起きてもサービスを継続できる性質）をどこまで確保するかも自分の判断です。ALBを何AZに配置するか、RDSをどう冗長化するかを、誰も代わりに決めてくれません。

「自由度が高いが知識が必要」とは、この3つの責任を引き受けるかどうかの話だと考えると具体的になります。

## AWSでの具体例

判断のしかたを、要件から逆に引く形で整理します。

```text
   Requirement                        ► Choice

   Static site, small team            ► Netlify / Vercel
   Preview deploys, fast iteration    ► Netlify / Vercel
   Private network segmentation       ► AWS (VPC)
   DB must not face the internet      ► AWS (Private Subnet + RDS)
   Integrate with existing AWS assets ► AWS
   Fine-grained cache / origin design ► AWS (CloudFront)
```

**Netlify / Vercel が向いている場面。** コーポレートサイトやドキュメントサイト、ブログのような静的サイト。プレビューデプロイを活かして高速に反復したいプロジェクト。インフラ担当者がおらず、フロントエンドエンジニアだけで運用するチーム。これらでAWSを選ぶと、得られる利益に対して管理コストが見合わないことが多くなります。

**AWSが向いている場面。** データベースを外部から到達不能な位置に置くことが要件の場合。社内システムなど特定のネットワークからのみアクセスさせたい場合。既にAWS上に別システムがあり同じVPC内で連携させたい場合。キャッシュやオリジンの構成を細かく制御したい場合。責任範囲を自分で持てることが、そのまま利点になります。

**両方を組み合わせる選択肢もあります。** フロントエンドはVercel、バックエンドAPIはAWSのALB + EC2、と分けるのは一般的な構成です。二者択一ではありません。

## フロントエンド開発との関係

Netlifyの管理画面にある「Build command」「Publish directory」という2つの入力欄は、[第13章](./13-architecture-static.md)の `astro build` と `aws s3 sync dist/ s3://my-site-bucket` に対応しています。「Domain management」でドメインを追加する操作は、Route 53のホストゾーンにAliasレコードを作る操作です。証明書の欄に何も入力しなくてよいのは、ACMに相当する処理が自動化されているからです。

Vercelでの `getServerSideProps` や Route Handlers は、[第14章](./14-architecture-server.md)ではPrivate SubnetのEC2上で動くNode.jsプロセスでした。「Functions」のリージョン設定は、EC2をどのリージョンのSubnetに置くかという選択に相当します。

この対応づけができるようになったこと自体が、この教科書の目的でした。**AWSの学習は、大量のサービス名を覚える作業ではありません。Webサービスを構成する部品が何であり、その部品同士がどういう関係で繋がっているのかを理解する作業です。** Netlify や Vercel を使い続けるとしても、この理解があれば、ビルドが失敗したときもキャッシュが更新されないときもDBに繋がらないときも、「どの層の話なのか」を切り分けられます。

## よくある勘違い

> **勘違い**: Netlify や Vercel は簡易的な仕組みで、本格的なサービスはAWSで作るべきだ。
> **実際は**: 用途の違いです。静的サイトや小〜中規模のアプリケーションでは、プラットフォームのほうが運用負荷とコストの両面で合理的な場面が多くあります。

> **勘違い**: Netlify や Vercel を使えば、インフラの知識はまったく不要である。
> **実際は**: 隠蔽されているだけで、DNSの伝播、キャッシュの挙動、実行環境のリージョンといった概念は表に出てきます。理解していれば、トラブル時の切り分けが速くなります。

> **勘違い**: AWSに移行すれば必ず安くなる。
> **実際は**: 部品ごとの課金であり、たとえばNAT Gatewayは起動している時間とデータ量の両方に課金されます。構成次第でどちらが安いかは変わります。

> **勘違い**: NetlifyかAWSか、どちらか一方を選ばなければならない。
> **実際は**: フロントエンドをVercel、バックエンドAPIをAWSに置くといった組み合わせは一般的です。要件ごとに適したものを選べます。

## この章で覚えるべきポイント

- [ ] Netlify / Vercel が隠蔽しているのは、ビルド・配置・CDN・HTTPS・DNS・キャッシュ・実行環境・スケーリング・ネットワーク・インフラ管理
- [ ] 静的サイト1本をAWSで組むと、Route 53・CloudFront・ACM・S3・CIの5要素が必要になる
- [ ] サーバーアプリではVPC以下の要素が加わり、おおよそ14種類前後まで増える
- [ ] 違いの本質は、ネットワーク・セキュリティ・インフラ設計の責任を誰が持つかという境界線
- [ ] 静的サイトや小規模はNetlify / Vercel、ネットワーク分離や既存AWS資産との統合はAWSが向く
- [ ] AWSはサービス名の暗記ではなく、部品と部品同士の関係を理解する対象である

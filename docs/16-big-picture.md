# 第16章 頭の中に持っておくAWS全体図

> **この章でわかること**
> - 静的サイト構成とサーバーアプリ構成を、1枚の図として頭の中に置ける
> - 各部品が「VPCの中か外か」「Publicか Privateか」を即答できる
> - ブラウザにURLを入力してから画面が出るまでの経路を、2パターンとも言葉で説明できる
> - 新しい案件で「静的でよいか、サーバーが要るか」を最初に判断できる
>
> **前の章とのつながり**: 第13〜15章で、部品を静的サイト構成とサーバーアプリ構成に組み上げ、Netlify / Vercel との違いも整理しました。この章では、そのすべてを1枚の図にまとめ直します。

ここまで16章分の部品が登場しました。しかし実務で必要なのは、部品の一覧を思い出せることではなく、**1枚の図を白紙に描けること**です。この章は、その1枚を作るための章です。

## 全体図

次の図が、本書のゴールです。上段が入口（VPCの外側）、下段がVPCの内部で、上段の右側から下段へ経路が続いています。1枚の図を上下2段に分けて表示しているだけなので、続きものとして読んでください。

**全体図（上段: 入口）**

```text
                     User (Browser)
                           │
                           ▼
                        Route 53          (DNS / Alias record)
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
         CloudFront                    ALB
     (CDN / HTTPS / Cache)        (Public Subnet)
              │                         │
              ▼                         ▼
             S3                [ continues below ]
     (dist/ : HTML, CSS, JS)
```

左が静的サイトの経路（図A）、右がサーバーアプリの経路（図B）です。CloudFront と S3 はVPCの外側にあるサービスで、ALB から下はVPCの中に入ります。

**全体図（下段: VPC内部）**

```text
            Internet
               │
               ▼
      ┌─── Internet Gateway ───┐
      │                        │
┌─────┴────────── VPC ─────────┴─────┐
│ 10.0.0.0/16                        │
│                                    │
│  ┌─── Public Subnet 10.0.1.0/24 ─┐ │
│  │   ALB                         │ │
│  │   NAT Gateway                 │ │
│  └───────────────────────────────┘ │
│                 │                  │
│                 ▼                  │
│  ┌─── Private Subnet 10.0.2.0/24 ┐ │
│  │   EC2  (App / Auto Scaling)   │ │
│  │   RDS  (Database)             │ │
│  └───────────────────────────────┘ │
│                                    │
└────────────────────────────────────┘
```

Security Group は図に描かれていませんが、ALB・EC2・RDS のそれぞれに付いています。図に現れない理由は、Security Group が「場所」ではなく「リソースに付く許可設定」だからです（第8章）。Route Table も同様で、Public Subnet と Private Subnet のそれぞれに1つずつ関連付けられています。

なお、この図は説明のための簡略図です。実運用では Public / Private ともに2つ以上のAZにSubnetを作ります。ALB もRDSのDBサブネットグループも、2AZ以上を要求するためです（第9章・第10章）。

## 部品ごとの役割一覧

| 部品 | 一言でいうと | たとえ | 置かれる場所 | 学んだ章 |
|---|---|---|---|---|
| Route 53 | ドメイン名をIPやAWSサービスに変換する | AWSが運営する住所録 | VPC外（グローバル） | [第4章](./04-route53.md) |
| CloudFront | 世界中の拠点からコピーを配る | 各地の前線倉庫・コンビニ | VPC外（グローバル） | [第12章](./12-cloudfront.md) |
| S3 | ファイルを置く | 巨大な倉庫・ロッカー | VPC外（リージョン単位） | [第11章](./11-s3-ssg.md) |
| VPC | 自分専用のネットワーク領域 | 自分専用に借りた土地・敷地 | リージョン内 | [第5章](./05-vpc-subnet.md) |
| Subnet | VPCを用途別に切った区画 | 敷地内の区画 | VPC内（1つのAZに属する） | [第5章](./05-vpc-subnet.md) |
| Internet Gateway | VPCとインターネットの境界 | 敷地の正門 | VPCにアタッチ | [第6章](./06-igw-routetable.md) |
| Route Table | 宛先ごとの行き先ルール | カーナビ / 道路標識 | Subnetに関連付け | [第6章](./06-igw-routetable.md) |
| NAT Gateway | 中から外への通信だけ通す | 通用口 | VPC内 / Public Subnet | [第7章](./07-nat-gateway.md) |
| Security Group | どの通信を通すかの許可設定 | 建物の入口に立つ門番 | VPC内 / リソース（ENI）単位 | [第8章](./08-security-group.md) |
| ALB | リクエストを複数台へ振り分ける | 受付・案内係 | VPC内 / Public Subnet（2AZ以上） | [第9章](./09-alb-autoscaling.md) |
| Auto Scaling | EC2の台数を自動で増減する | 混雑に応じてスタッフを増減する店長 | VPC内 / EC2の配置先に従う | [第9章](./09-alb-autoscaling.md) |
| EC2 | プログラムを動かす | 敷地に建てた建物（事務所） | VPC内 / Private Subnet（ALB導入後） | [第2章](./02-ec2.md) |
| RDS | データを預かるマネージドDB | 金庫室・書庫 | VPC内 / Private Subnet | [第10章](./10-rds.md) |

この表で押さえてほしいのは、**VPCの中にある部品と外にある部品がはっきり分かれている**という点です。Route 53・CloudFront・S3 はVPCに属しません。だから静的サイト構成では、VPCもSubnetもRoute Tableも一切登場しないのです。

## データの旅

### 旅1: 静的サイトの場合

ブラウザに `https://example.com` と入力してから画面が出るまでを、順に追います。

1. ブラウザが `example.com` のIPアドレスを知るために、DNSへ問い合わせます。手元にキャッシュがあればここで終わり、なければルートサーバー → TLDサーバー → 権威DNSサーバーの順にたどります（第3章）。
2. `example.com` の権威DNSサーバーはRoute 53です。ホストゾーンに登録されたAレコードのAliasが、CloudFrontを指し示しています（第4章）。
3. ブラウザは、返ってきたIPアドレスのポート443へHTTPSで接続します。接続先は、ユーザーに地理的に近いCloudFrontのエッジロケーションです（第12章）。
4. CloudFrontがHTTPSを終端します。使われる証明書はACMがus-east-1で発行したものです（第12章）。
5. エッジロケーションに目的のファイルのコピーがあれば（キャッシュヒット）、その場で返します。旅はここで終わりです。
6. コピーがなければ（キャッシュミス）、CloudFrontはオリジンであるS3へ取りに行きます。S3バケットは非公開で、OACによって署名されたCloudFrontのリクエストだけを受け付けます（第11章・第12章）。
7. S3が `index.html` を返します。CloudFrontはそれをTTLの期間だけエッジロケーションに保存し、同時にブラウザへ返します。
8. ブラウザがHTMLを解析し、CSS・JS・画像を同じ経路で取得して、画面が表示されます。2回目以降は多くがキャッシュヒットになります。

**EC2もVPCもSubnetも1つも登場していません。** これが「静的サイトにサーバーは要らない」ということの意味です。

### 旅2: サーバーアプリの場合

同じ `https://example.com` でも、ログインが必要でデータベースを参照するアプリケーションの場合はこうなります。

1. ブラウザがDNSへ問い合わせます。ここまでは旅1と同じです。
2. Route 53のAレコードのAliasが、今度はALBを指しています（第4章・第9章）。
3. ブラウザはALBへHTTPSで接続します。ALBはPublic Subnetに置かれ、2つ以上のAZにまたがっています。ALB自身がインターネットから到達可能なのは、そのSubnetのRoute Tableに `0.0.0.0/0 → igw-xxxx` があるからです（第6章）。
4. ALBのSecurity Group（門番）が、インターネットからの443番を許可しているかを確認します。許可されていれば通ります（第8章）。
5. ALBはリスナーで受け取ったリクエストを、ターゲットグループに登録されているEC2のうち、ヘルスチェックに合格しているものへ振り分けます（第9章）。
6. EC2はPrivate Subnetにあります。EC2のSecurity Groupは「ALBのSecurity Groupからの通信のみ許可」に設定されているため、インターネットから直接叩かれることはありません（第8章・第9章）。
7. EC2上のアプリケーションがリクエストを処理し、必要なデータをRDSに問い合わせます。RDSも同じPrivate Subnetにあり、そのSecurity Groupは「EC2のSecurity Groupからの3306番のみ許可」です（第10章）。
8. RDSが結果を返し、EC2がHTMLやJSONを組み立ててALBへ返し、ALBがブラウザへ返します。Security Groupはステートフルなので、この戻りの通信に追加の許可設定は不要です（第8章）。
9. アクセスが増えてCPU使用率が上がると、Auto Scaling GroupがEC2を追加で起動します。新しいEC2は自動的にターゲットグループに登録され、ヘルスチェックを通過した時点から振り分け対象に加わります（第9章）。
10. なお、このEC2がOSのアップデートや外部APIの呼び出しのために外へ出るときは、Private SubnetのRoute Tableに従ってNAT Gatewayを経由し、そこからInternet Gatewayを通って外に出ます（第7章）。

旅1と旅2で共通しているのは、最初の2ステップ（DNSとRoute 53）だけです。**3ステップ目から先が完全に別の経路になる**という点が、この2つの構成の本質的な違いです。

## 設計時の判断フロー

新しい案件で最初に決めるべきなのは、この分岐です。

```text
        New project
             │
             ▼
   Does a server need to compute
   per request ?
   (login / DB / API / SSR)
             │
      ┌──────┴──────┐
      ▼             ▼
     No            Yes
      │             │
      ▼             ▼
  Static site   Server app
   (Figure A)    (Figure B)
      │             │
      ▼             ▼
  Route 53      Route 53
  CloudFront    ALB (Public Subnet)
  S3 (OAC)      EC2 (Private Subnet)
                RDS (Private Subnet)
                + VPC / Subnet / IGW
                + Route Table / NAT GW
                + Security Group
```

判断の基準は「サーバーで計算が必要か」の一点です。ログイン処理、データベースの読み書き、リクエストごとに内容が変わるページの生成（SSR）、外部APIを秘密鍵付きで叩く処理。これらが1つでもあれば右側です。ブログ、コーポレートサイト、ドキュメント、ランディングページのように、ビルド時に出力が確定するものは左側です。

左右で必要な部品の数がまったく違うことに注目してください。左は3つ、右はネットワークまで含めると10近くあります。この差が、そのままNetlify / Vercel を使うかAWSを自分で組むかの判断材料にもなります（第15章）。

なお、この分岐は「どちらか一方」とは限りません。実際の案件では、静的なページはCloudFront + S3で配信し、APIだけをALB + EC2で受ける、という組み合わせがよく使われます。その場合もRoute 53のホストゾーンで、`example.com` はCloudFrontへ、`api.example.com` はALBへ、とレコードごとに振り分けるだけです（第4章）。**部品の組み合わせ方が変わるだけで、部品そのものは変わりません。**

## この章で覚えるべきポイント

- [ ] 全体図を白紙に描ける。上段（User / Route 53 / CloudFront / S3・ALB）と下段（VPC内部）に分けて描けばよい
- [ ] Route 53・CloudFront・S3 はVPCの外、ALB・EC2・RDS・NAT Gateway はVPCの中にあると即答できる
- [ ] Public Subnet に置くのはALBとNAT Gateway、Private Subnet に置くのはEC2とRDS、と即答できる
- [ ] 静的サイトの旅とサーバーアプリの旅を、それぞれ番号順に説明できる
- [ ] 「サーバーで計算が必要か」を起点に、構成を選べる
- [ ] Security Group と Route Table は図に現れない部品だが、通信の成立には必須であると説明できる

### Solutions Architect Associate ではこう問われる

試験では、この章のような全体図が問題文の前提として与えられ、「この構成に何が足りないか」「どこを変えれば要件を満たすか」を答える形が中心になります。個々のサービスの定義を問う設問より、**構成図を読んで欠けている部品を特定する**設問のほうが多いと考えてください。本章の一覧表にある「VPCの中か外か」「PublicかPrivateか」は、その判断の最短ルートになります。特に「RDSがPublic Subnetにある」「NAT GatewayがPrivate Subnetにある」「ALBが1AZしかない」といった構成は、それ自体が誤りの選択肢として頻繁に登場します。

# 第4章 Route 53 — AWSの住所録

> **この章でわかること**
> - Route 53がAWSの中でどんな役割を持つサービスかを説明できる
> - ホストゾーンと、Aレコード・CNAME・Aliasレコードの違いを説明できる
> - CloudFrontやALB、S3を指す際にAliasレコードが使われる理由を説明できる
> - Route 53が「DNSサービス」であり、CDNやサーバーそのものではないことを説明できる
>
> **前の章とのつながり**: 前章では、ドメイン名をIPアドレスに変換するDNSという仕組み一般について説明しました。この章では、AWSがそのDNSの仕組みをサービスとして提供している「Route 53」を具体的に見ていきます。

## なぜこれが必要なのか

DNSの仕組み自体は、どの事業者が提供していても同じです。では、なぜAWSはわざわざ自前のDNSサービスであるRoute 53を用意しているのでしょうか。すでにドメインを取得したお名前.comなどのレジストラでもDNSの設定はできるのに、AWSの構成ではRoute 53が使われることが多いのはなぜか。この疑問に答えるには、Route 53がAWSの他のサービス(CloudFront、ALB、S3など)と密に連携する設計になっていることを理解する必要があります。

## まずはざっくり: 中学生にもわかる説明

前の章で、DNSは「電話帳」のようなものだと説明しました。Route 53は、AWSという会社が用意している電話帳サービスです。世の中にはいくつも電話帳を作っている会社がありますが、AWSの中で建てた建物（EC2など)やAWSが用意した倉庫（S3）、各地に置いた前線倉庫（CloudFront）を案内するときには、AWS自身が作った電話帳を使うほうが都合よく連携できるようになっています。

## 身近なたとえ

Route 53は「AWSが運営する住所録」です。AWSという巨大な国の中に建物や施設を作ったとき、その国が発行している公式の住所録に登録しておけば、道案内がスムーズに行われます。他社の住所録を使うこともできますが、その国独自の仕組み（あとで説明するAliasレコードなど）は、その国の住所録でなければ使えません。

## 技術的にはこういうこと

Route 53は、AWSが提供するDNSサービスです。ドメインの管理は**ホストゾーン**という単位で行います。ホストゾーンとは、あるドメイン（例えば `example.com`）についてのDNSレコードをまとめて管理する箱のようなものです。ホストゾーンの中に、複数の**レコード**を登録していきます。

代表的なレコードには次のものがあります。

- **Aレコード**: ドメイン名を直接IPアドレスに対応づけるレコードです。「example.com は 203.0.113.10 である」という形式で登録します。
- **CNAMEレコード**: あるドメイン名を、別のドメイン名の別名として登録するレコードです。「www.example.com は xxxx.cloudfront.net の別名である」という形式で登録します。
- **Aliasレコード**: Route 53が独自に提供する拡張機能で、AレコードやCNAMEレコードのように見えつつ、実際にはCloudFront、ALB、S3といったAWSのサービスを直接指し示すことができる特別なレコードです。

CloudFront（AWSのCDN、詳しくは第12章）やALB（負荷分散装置、詳しくは第9章）、S3（詳しくは第11章）を指す際には、このAliasレコードが使われます。その理由は2つあります。

1つ目は、**Zone Apexにはドメイン仕様上CNAMEを使えない**という制約です。Zone Apex（ゾーンエイペックス）とは、`www` のようなサブドメインが付いていない、ドメインの頂点そのもの（`example.com` 自体）を指します。DNSの仕様上、CNAMEレコードはその名前に他のレコードと同居することができません。一方でZone Apexには、SOAレコードやNSレコード（どちらもそのゾーンの管理情報を示すレコードです）が必ず存在します。この2つが同居している以上、同じ名前にCNAMEを追加で置くことはできず、結果としてZone Apexには CNAMEを設定できないことになります。しかし「`example.com` そのものにアクセスしたら、CloudFrontに転送したい」というニーズは非常に多くあります。Aliasレコードは見た目上Aレコードの形式を取りながら、CloudFrontなどのAWSサービスを指せるため、この制約を回避できます。

2つ目は、**Aliasレコードにはクエリ料金がかからない**という点です。通常のDNSレコードへの問い合わせにはRoute 53の利用料金が発生しますが、Aliasレコードを経由してAWSサービスを指す場合の問い合わせには料金がかかりません。

```text
        Browser
           │
           ▼
      Route 53   (Hosted Zone: example.com)
           │       example.com  ► Alias ► CloudFront
           │       www.example.com ► CNAME ► xxxx.cloudfront.net
           ▼
      CloudFront
           │
           ▼
            S3
```

## AWSでの具体例

実際の設定では、Route 53のコンソールでホストゾーンを開き、レコードを追加します。Zone Apexの `example.com` をCloudFrontに向けたい場合は、レコードタイプを「A」にした上で、「エイリアス」を有効にし、対象としてCloudFrontディストリビューションを選択します。`www.example.com` のようなサブドメインの場合は、同様にAliasを使うことも、通常のCNAMEで `xxxx.cloudfront.net` を直接指定することもできますが、AWSサービスを指す場合は料金面・仕様面の理由からAliasを使うのが基本です。

```text
Hosted Zone: example.com
┌───────────┬───────────────────┬────────────────────┐
│ Type      │ Name              │ Target             │
├───────────┼───────────────────┼────────────────────┤
│ A (Alias) │ example.com       │ CloudFront         │
│ A (Alias) │ api.example.com   │ ALB                │
│ CNAME     │ blog.example.com  │ xxxx.wordpress.com │
└───────────┴───────────────────┴────────────────────┘
```

（Type=種別、Name=登録するドメイン名、Target=参照先。Zone Apexである `example.com` と `api.example.com` はAliasでCloudFront・ALBを指し、サブドメインの `blog.example.com` は通常のCNAMEで別サービスを指しています。）

## フロントエンド開発との関係

Netlifyや Vercelでは、ダッシュボード上で独自ドメインを入力し、指示されたレコード（多くはAレコードかCNAME）をドメインの管理画面に追加するだけで済みます。裏側では、Netlify・Vercelがそれぞれ自社のDNS基盤やCDNの入り口を用意しており、利用者はその詳細を意識する必要がありません。AWSでRoute 53を使う場合は、この「ドメインとCDN・サーバーを結びつける」作業を、ホストゾーンの作成からレコードタイプの選定まで自分で行うことになります。特に「Zone ApexにはCNAMEが使えないので、AWSではAliasという専用の仕組みがある」という点は、Netlify・Vercelでは意識せず済んでいた仕様上の制約が、AWSでは表に出てくる典型例といえます。

## よくある勘違い

> **勘違い**: Route 53はCDNやWebサーバーの一種である。
> **実際は**: Route 53はあくまでDNSサービスであり、ドメイン名をIPアドレスや他のAWSサービスに変換する役割のみを持ちます。実際にコンテンツを配信するのはCloudFrontやS3、EC2などの別のサービスです。

> **勘違い**: AWSのサービスを指すときも、普通のCNAMEで十分である。
> **実際は**: Zone Apex（`example.com` そのもの）にはDNS仕様上CNAMEを置けません。CloudFrontやALB、S3を指すにはAliasレコードを使うのが基本です。

> **勘違い**: AliasレコードはCNAMEの単なる別名で、機能的な違いはない。
> **実際は**: AliasレコードはZone Apexに設定できる点、そしてAWSサービスへの問い合わせにクエリ料金がかからない点で、通常のCNAMEやAレコードとは異なります。

> **勘違い**: ドメインを取得した会社（レジストラ）でしかDNSの設定はできない。
> **実際は**: ドメインの登録（レジストラでの管理）と、実際に名前解決を行うDNSサービスの指定は分離できます。レジストラ側で「このドメインのDNSはRoute 53に任せる」という設定（ネームサーバーの変更）を行うことで、Route 53側でレコードを管理できるようになります。

## この章で覚えるべきポイント

- [ ] Route 53がAWSの提供するDNSサービスであり、ホストゾーン単位でドメインのレコードを管理すると説明できる
- [ ] Aレコード・CNAMEレコード・Aliasレコードの違いを説明できる
- [ ] Zone ApexにCNAMEを設定できない理由を説明できる
- [ ] CloudFront・ALB・S3を指す際にAliasレコードが使われる2つの理由（Zone Apex制約の回避、クエリ料金がかからない）を説明できる
- [ ] Route 53自体はDNSサービスであり、CDNやサーバーそのものではないと説明できる

### Solutions Architect Associate ではこう問われる

「Zone Apex（例: `example.com` 自体）にCloudFrontやALBを紐付けたい場合、CNAMEではなくAliasレコードを使う」という判断が定番の論点です。CNAMEとAliasの違い（DNS仕様上の制約、クエリ料金の有無）を問う設問が典型的で、「なぜAliasを選ぶべきか」という理由まで含めて理解しているかが問われます。単に「Route 53を使う」という選択肢だけでなく、レコードタイプの使い分けが正解を分けるポイントになりやすい分野です。

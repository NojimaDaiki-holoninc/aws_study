# 第6章 Internet GatewayとRoute Table — 正門とカーナビ

> **この章でわかること**
> - なぜVPCを作ってEC2を置いただけではインターネットにつながらないのかを説明できる
> - IGWをアタッチしただけでは通信が通らない理由をRoute Tableの中身から説明できる
> - 「Public Subnetとは何か」をたとえではなく定義として説明できる
> - EC2がインターネットと通信するために経路のほかに何が必要かを説明できる
>
> **前の章とのつながり**: 第5章でVPC（`10.0.0.0/16`）とSubnet（`10.0.1.0/24` / `10.0.2.0/24`）を作りましたが、「この時点ではインターネットから一切到達できない」と書いたまま終わっています。この章でその続きを解きます。

## なぜこれが必要なのか

第5章の最後で、Public Subnetと名付けたSubnetにEC2を起動し、プライベートIPアドレス `10.0.1.42` も割り当てられました。ところがブラウザから接続しても何も返ってきません。土地を借り、区画を引き、建物を建て、名前も `public` と付けたのにです。

本書全体で最も重要な問いはここです。**なぜVPCを作っただけではインターネットにつながらないのか。** そしてもう一段深く、**なぜ「正門」であるInternet Gatewayを建てただけでも、まだつながらないのか。** この問いに答えられると、AWSのネットワークは「サービス名の羅列」から「原因と結果でつながった仕組み」に変わります。逆にここを飛ばすと、原因の切り分けができません。

## まずはざっくり: 中学生にもわかる説明

前の章で借りた土地は、周りを塀で囲われています。まず必要なのは、塀に穴を開けて門を作ることです。この門がInternet Gatewayです。

ところが、門を建てただけでは誰も出入りしません。土地の中にいる人が「外に行くにはあの門を通ればいい」ということを知らないからです。荷物を持った配達員が、どこへ届ければいいか分からず立ち尽くしている状態です。

必要なのは敷地の中に**道路標識を立てること**、「ここではないどこか宛ての荷物は、あの門から出なさい」という標識です。これがRoute Tableで、区画ごとに立てます。表の区画には立て、奥の区画には立てません。

つまり、外とつながる区画とそうでない区画の違いは、**建物の種類でも区画の名前でもなく、その区画に立っている標識の内容**なのです。

## 身近なたとえ

Internet Gatewayは敷地の正門です。VPCという土地に1つ取り付けますが、門はそこにあるだけで通行を管理も許可もしません。

Route Tableはカーナビ、あるいは道路標識です。表の区画のカーナビには「敷地内の宛先は敷地内で完結。それ以外は全部、正門へ」と書いてあります。奥の区画のカーナビには「敷地内の宛先は敷地内で完結」としかないので、外へは出られません。門を建てる作業とカーナビに行き先を書き足す作業は**別々**なのです。

なお、この章で扱うのは「どの道を通るか」だけで、通ろうとした人の身元を確認する係員は第8章のSecurity Group（門番）です。**門と門番は別物**です。

## 技術的にはこういうこと

**Internet Gateway。** IGW（Internet Gateway）とは、VPCとインターネットの間で通信を成立させるためのVPCコンポーネントで、1つのVPCにつき1つアタッチ（接続）します。AWSが運用を代行する**マネージド**な仕組みで、冗長化（一部が壊れても全体が止まらない構成）されています。役割は、Route Tableの出口として指定できるようになることと、プライベートIPアドレスとパブリックIPアドレスの相互変換です（パブリックIPを持つリソース1つに対する1対1の変換です。第7章で扱うNAT Gatewayの、多数のプライベートIPを1つのパブリックIPにまとめる変換とは別物です）。

重要なのは、**IGWをアタッチした瞬間には、まだ何の通信も変化しない**という点です。「出口として指定できる対象」が1つ増えただけです。

**Route Table。** Route Table（ルートテーブル）とは、「宛先IPアドレスの範囲」と「渡す先（ターゲット）」の対応表です。通信を発信すると、発信元Subnetに関連付けられたRoute Tableが参照され、最も適合する行が選ばれます。VPCを作ると**メインルートテーブル**が1つ自動作成されます。

| Destination（宛先） | Target（渡す先） | |
|---|---|---|
| `10.0.0.0/16` | `local` | 最初からある |
| `0.0.0.0/0` | `igw-0a1b2c3d4e5f6a7b8` | 自分で追加する |

これが答えです。**デフォルトでは1行目、VPC内部宛て（`10.0.0.0/16`）の `local` 経路しか存在しません。** `local` は「VPCの中で完結して届ける」という意味の予約された指定です。

EC2が `10.0.2.30`（同じVPC内のRDS）へ通信すればこの行に一致して届きます。しかしインターネット上のアドレス宛てでは一致する行がありません。**行き先が分からない通信は破棄されます。** これが「VPCを作っただけではつながらない」の正体で、だから2行目の追加が必要なのです。

`0.0.0.0/0` は「すべてのIPアドレス」を表すCIDR表記で（`/0` は何も固定しない＝全部）、**デフォルトルート**と呼びます。Route Tableは最も長く一致する行を優先するため、`10.0.0.0/16` 宛てはそちらが使われ、残りすべてが `0.0.0.0/0` の行に落ちてIGWへ渡されます。`local` 経路は削除も変更もできません。

**そして、Public Subnetの定義。** Route Tableは作っただけでは使われず、**どのSubnetがそれを参照するのか**を明示的に関連付ける必要があります（AWSでは Subnet associations と呼びます）。ここまでを整理すると、定義が導けます。

> **Public Subnetとは、`0.0.0.0/0` の宛先がInternet Gatewayを向いているRoute Tableが関連付けられたSubnetのことです。**

Subnetの種類でも名前でもなく、関連付けられたRoute Tableの中身だけが、そのSubnetをPublicにします。逆に**Private Subnetとは、そのようなRoute Tableが関連付けられていないSubnet**のことです。第5章で「Route Tableで性質が決まる」と書いたのは、このことでした。

**もう1つ必要なもの、パブリックIPアドレス。** 経路が通っても、EC2自身がパブリックIPアドレスを持たなければ通信できません。自動で割り当てられるプライベートIPアドレス（`10.0.1.42`）はインターネット上に存在せず、外部から返信を送りようがないからです。起動時の「パブリックIPの自動割り当て」は手軽ですが、**停止して再起動すると別のアドレスに変わります**。**Elastic IP（EIP）**なら固定でき、停止・起動をまたいでも変わりません。

まとめると、通信の成立には次の3条件が必要です。

```text
       Internet
          │
          ▼
    Internet Gateway            (1) IGW attached to VPC
          │
┌─────────┴────── VPC 10.0.0.0/16 ─────────┐
│                                          │
│  Route Table (public)                    │
│    10.0.0.0/16  ► local                  │
│    0.0.0.0/0    ► igw-xxxx               │  (2) route added
│          │                               │
│          │  associated                   │  (3) associated
│          ▼                               │
│  ┌─── Public Subnet 10.0.1.0/24 ───────┐ │
│  │   EC2 (App)                         │ │
│  │     private IP 10.0.1.42            │ │
│  │     public  IP 54.xxx.xxx.xxx       │ │  ◄── public IP required
│  └─────────────────────────────────────┘ │
│                                          │
└──────────────────────────────────────────┘
```

この3つが揃って初めてSubnetはPublicになり、さらにEC2がパブリックIPを持ってようやく外と通信できます。1つ欠ければ成立しません。

## AWSでの具体例

マネジメントコンソール（AWSの管理画面）での作業は5つです。

**1. Internet Gatewayを作成してアタッチする。** 作成直後の State は `Detached` で何の役にも立ちません。`my-app-vpc` にアタッチすると `Attached` になり、`igw-0a1b2c3d4e5f6a7b8` というIDが使えます。

**2. Route Tableを作成する。** 名前は `my-app-public-rt`、VPCは `my-app-vpc`。この時点では `10.0.0.0/16 → local` の1行だけです。

**3. 経路を追加する。** Destination に `0.0.0.0/0`、Target に Internet Gateway（`my-app-igw`）を指定して保存します。

**4. Subnetに関連付ける（Subnet associations）。** `my-app-public-1a`（`10.0.1.0/24`）を選んで保存します。**この操作を忘れるのが最も多い設定漏れです。** 関連付けのないSubnetは暗黙的にメインルートテーブル（`local` のみ）を使い続け、Privateのままになります。`10.0.2.0/24` には何もしません。`local` だけのままにしておく、それがPrivateだということです。

**5. EC2にパブリックIPを持たせる。** 起動時に Auto-assign public IP を `Enable` にし、Public IPv4 address に値が入っていれば成功です。固定するなら Elastic IP を関連付けます。

ここまで設定してもHTTPでアクセスできないなら、残る原因は本章の範囲外、**Security Group**（第8章）が80番・443番ポートを許可していないケースです。経路が通っていることと通信が許可されていることは、別のレイヤーの話です。

## フロントエンド開発との関係

Netlify や Vercel にAstroプロジェクトをデプロイすると、ビルドが終わった瞬間にURLが発行され世界中からアクセスできます。Route Tableを触った覚えも `0.0.0.0/0` と入力した覚えもないはずです。

「デプロイしたら勝手に公開される」のは当たり前ではありません。素のAWSでは、IGWの作成とアタッチ、Route Tableの作成、経路の追加、Subnetへの関連付け、パブリックIPの付与という5つの独立した操作が必要です。Netlify/Vercelは、これらを済ませたインフラの上にあなたの `dist/` を置いているのです。

これは「Vercelは楽で、AWSは面倒」という話ではなく、**デフォルトがどちら側に寄っているか**の違いです。Netlify/Vercelは「公開する」用途に特化しているので公開がデフォルト。AWSは公開しないものも大量に扱うため、**何もしなければ何も通らない**のがデフォルトです。

これはフロントエンドの `NEXT_PUBLIC_` プレフィックスの発想に近く、明示的に宣言したものだけが公開されます。AWSでは `0.0.0.0/0 → igw-xxxx` という1行が、その公開宣言にあたります。

## よくある勘違い

> **勘違い**: Internet GatewayをVPCにアタッチすれば、VPC内のリソースはインターネットと通信できる。
> **実際は**: アタッチしただけでは何も変わりません。`0.0.0.0/0 → igw-xxxx` を追加し、そのRoute TableをSubnetに関連付けて初めて経路が成立します。

> **勘違い**: Internet Gatewayは通信を許可・拒否するファイアウォールである。
> **実際は**: IGWは可否を判断しません。どの通信を通すかを決めるのはSecurity Group（第8章）です。IGWは門であり、門番ではありません。

> **勘違い**: Subnetの名前を `public` にしたので、そこはPublic Subnetである。
> **実際は**: 名前は人間向けのタグです。Public Subnetとは「`0.0.0.0/0` がIGWを向くRoute Tableが関連付けられたSubnet」のことです。

> **勘違い**: 経路さえ通っていれば、EC2はインターネットと通信できる。
> **実際は**: EC2自身がパブリックIPアドレス（またはElastic IP）を持つ必要があります。プライベートIPアドレスしか持たなければ、外部から返信を届ける宛先がありません。

## この章で覚えるべきポイント

- [ ] デフォルトのRoute Tableには `10.0.0.0/16 → local` しかなく、行き先が分からない通信は破棄されるため外部と通信できない
- [ ] Internet Gatewayは1つのVPCに1つアタッチするが、それだけでは通信は変化しない
- [ ] インターネットへ出るには `0.0.0.0/0 → igw-xxxx` を追加する。`0.0.0.0/0` は「すべての宛先」を意味するデフォルトルート
- [ ] Route TableはSubnetに関連付けて初めて有効になる。関連付け忘れが最も多い設定漏れ
- [ ] Public Subnetとは、`0.0.0.0/0` がIGWを向くRoute Tableが関連付けられたSubnetのことである
- [ ] 経路に加えEC2にはパブリックIPまたはElastic IPが必要。通信の許可・拒否はSecurity Group（第8章）という別レイヤーが担う

---

### Solutions Architect Associate ではこう問われる

「EC2にインターネットからアクセスできない。原因はどれか」という**トラブルシューティング型**で頻出します。IGW未アタッチ、`0.0.0.0/0` の経路がない、Route TableがSubnetに未関連付け、パブリックIPがない、Security Groupが該当ポートを許可していない。この5つを切り分けられるかが問われます。

「IGWもRoute Tableも正しい」とあれば答えはパブリックIPかSecurity Group側、「Subnetを作ってEC2を置いたが通信できない」だけなら経路追加が正解になりやすい形です。

また経路選択では**より長い（具体的な）プレフィックスが優先される**という原則も問われます。`10.0.0.0/16 → local` と `0.0.0.0/0 → igw` が併存する場合、VPC内宛ては必ず `local` が使われます。

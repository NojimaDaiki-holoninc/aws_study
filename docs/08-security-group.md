# 第8章 Security Group — どの通信を通すかの門番

> **この章でわかること**
> - Route Table で道が通っているのに、なぜさらに許可設定が必要なのかを説明できる
> - Security Group がステートフルであること、許可ルールのみであることを説明できる
> - Security Group が Subnet 単位ではなくリソース単位で効くことを説明できる
> - ソースに別の Security Group を指定する書き方と、その利点を説明できる
>
> **前の章とのつながり**: 第6章と第7章で、Internet Gateway・Route Table・NAT Gateway を使って「通信の道」を作りました。しかし道が通っているだけでは、まだ通信は成立しません。

## なぜこれが必要なのか

第6章で Route Table に `0.0.0.0/0 → igw-xxxx` を書き、第7章で Private Subnet からの外向き経路も作りました。これで EC2 にブラウザからアクセスできるはず、と思ってURLを叩いても、多くの場合いつまでも応答が返ってきません。道は通っているのに、です。

仮に道さえ通っていれば全通信が届くとしたら、世界中の誰もがあなたのサーバーの SSH のポート（22番、サーバーに遠隔ログインするための入口）に到達できることになります。データベースのポートにも、開発用に立ち上げた3000番にも、です。

**道が通っていること**と、**その通信を通してよいか**は、別々に決められるべきものです。この後者を担当するのが Security Group です。第6章までが「どこへ向かうか」の話だったのに対し、この章は「そもそも入れるか」の話になります。

## まずはざっくり: 中学生にもわかる説明

大きなオフィスビルを想像してください。ビルの前まで道路が通っていて、誰でも建物の前までは来られます。しかし建物の入口には人が立っていて、名簿を持っています。

その人が見ているのは**入れる人のリスト**だけで、「この人は入れない」という追い出しリストは持っていません。名簿に載っていなければ、それだけで入れないからです。

もう1つ。中の人が外に出てまた戻ってくるとき、いちいち名簿は確認されません。行きを確認したなら、帰りは自動で通してもらえます。

そしてこの人が立っているのは、敷地の入口ではなく**建物ごとの入口**です。同じ敷地に建物が3つあれば、それぞれの入口に別の名簿を持った人が立ちます。

## 身近なたとえ

Security Group は**建物の入口に立つ門番**です。

第6章で Internet Gateway を「敷地の正門」と呼びました。門を通れば敷地には入れますが、その先、建物に入るには門番のチェックを受けなければなりません。この2段構えが VPC のセキュリティの基本形です。

門番は建物ごとに立ちます。事務所の門番と金庫室の門番は別人で、別のリストを持っています。金庫室の門番のリストには「事務所から来た人だけ」と書いてあり、正門を通ってきた人であってもそれ以外は入れません。

## 技術的にはこういうこと

**Security Group** は、AWS のリソースに対する仮想的なファイアウォールです。ファイアウォールとは、通信を検査して通すか通さないかを判断する仕組みを指します。特徴は次の4つです。

**1. リソース（ENI）単位で効く。** Security Group は Subnet ではなく**リソースに対して**紐付きます。正確には **ENI（Elastic Network Interface）**、つまりリソースが持つ仮想的なネットワークカードに適用されます。そのため、同じ Subnet に置いた2台の EC2 にまったく違うルールを設定できますし、異なる Subnet のリソースへ同じ Security Group を割り当てることもできます。「Subnet を分けたからルールも分かれる」という関係ではありません。

```text
┌─── Public Subnet 10.0.1.0/24 ──────────────────┐
│   ┌── EC2 (Web) ──┐      ┌── EC2 (Batch) ──┐   │
│   │  ENI ► app-sg │      │  ENI ► batch-sg │   │
│   │  allow 80/443 │      │  no 80/443      │   │
│   └───────────────┘      └─────────────────┘   │
└────────────────────────────────────────────────┘
```

（凡例）同じ Subnet 内でも、リソースごとに別の Security Group を割り当てられます。左の EC2 は80番・443番を許可し、右は許可していません。

**2. 許可（allow）ルールしか書けない。** 書けるのは「通してよい通信」だけで、「この通信を拒否する」というルールは存在しません。制限のように見えますが、何も書かなければ何も通らないため、**書き忘れが「うっかり全開放」にはならない**という安全側の設計です。デフォルトではインバウンド（外から入ってくる通信）は何も許可されていません。なお、ステートレスに動作し拒否ルールも書ける **Network ACL** という別の仕組みが Subnet 単位で存在しますが、本書では扱いません。

**3. ステートフルである。** **ステートフル**とは、通信の状態（どの通信がすでに始まっているか）を記憶して判断することを指します。ブラウザから EC2 の443番へリクエストが届き、インバウンドルールで443番が許可されていれば通ります。そして EC2 がレスポンスを返すとき、**その戻りはアウトバウンドルールを確認せずに自動的に通ります**。逆方向も同じで、`npm install` の外向き通信がアウトバウンドで許可されていれば、返ってくるパッケージのデータはインバウンドに何も書かなくても届きます。**「行きと帰りの両方を許可設定する必要がある」というのは誤りです。**

```text
     Internet                      EC2 + SG
        │  Request dst:443            │
        ├────────────────────────────►│  Inbound 443 : ALLOW
        │  Response                   │
        │◄────────────────────────────┤  Outbound : not checked
```

（凡例）インバウンドで443番を許可すれば、その応答はアウトバウンドの設定を確認されずに返ります。

**4. ルールの中身。** インバウンド／アウトバウンドの各ルールは、**プロトコル**（通信の方式。Web の通信は TCP）、**ポート**（用途を区別する番号。HTTP は80、HTTPS は443、SSH は22、MySQL は3306）、**ソース**（どこから来た通信を許可するか）で構成されます。

ソースの書き方は2つ。1つは **CIDR 表記**（`0.0.0.0/0` は「すべて」、`203.0.113.10/32` は「この1つのIPアドレスだけ」）。もう1つが重要で、**別の Security Group の ID を指定できます**。この場合「その Security Group が割り当てられたリソースから来た通信」という意味になり、EC2 が増減してIPが変わっても設定を直す必要がありません。

## AWSでの具体例

Web サーバーとデータベースの2階層を想定した、最小構成のインバウンドルールです。

| SG | Protocol | Port | Source | 意図 |
|---|---|---|---|---|
| app-sg (EC2) | TCP | 80 / 443 | `0.0.0.0/0` | 誰でも閲覧できる |
| app-sg (EC2) | TCP | 22 | `203.0.113.10/32` | 管理者のIPのみ |
| db-sg (RDS) | TCP | 3306 | `app-sg`（SG ID） | Web サーバーからのみ |

**SSH（22番）のソースを `0.0.0.0/0` にしないでください。** 世界中からのログイン試行を受け付けることを意味します。自分の接続元IPアドレスを `/32`（1アドレスだけ）で指定するのが基本です。

3306番のソースに CIDR ではなく `app-sg` を指定しているのがポイントです。「app-sg が付いているリソースからだけ通す」という意味になり、Web サーバーを何台に増やしてもこのルールを書き換える必要がありません。

```text
   Internet
      │
      │ 80 / 443 : from 0.0.0.0/0
      │ 22       : from 203.0.113.10/32
      ▼
  ┌── EC2 ──┐
  │  app-sg │
  └─────────┘
      │
      │ 3306 : from app-sg        ◄── source = SG ID
      ▼
  ┌── RDS ──┐
  │  db-sg  │
  └─────────┘
```

アウトバウンドはデフォルトで「すべて許可」のルールが1つ入っており、多くの場合そのままで構いません。

## フロントエンド開発との関係

Vercel の設定画面にある Deployment Protection やパスワード保護は、「誰にこのデプロイを見せるか」を決める設定です。AWS でそれに相当する、もっと低いレイヤーの設定が Security Group だと考えてください。Vercel では画面のトグル1つだったものが、AWS ではポート番号とソースIPを自分で書く作業になります。

ここで気をつけたいのが **CORS との違い**です。CORS（Cross-Origin Resource Sharing）でエラーが出たとき、通信は届いています。リクエストはサーバーまで到達しレスポンスも返っており、その上でブラウザがJavaScriptからのアクセスを拒否している状態です。CORS はブラウザ側のルール、Security Group はサーバーに届く前のネットワーク層のルールで、別のレイヤーです。CORS エラーを Security Group で直すことはできません。

## よくある勘違い

> **勘違い**: Security Group では、行きの通信と帰りの通信の両方を許可設定しなければならない。
> **実際は**: 必要ありません。Security Group はステートフルなので、インバウンドで443番を許可すれば、そのレスポンスはアウトバウンドの設定に関係なく返せます。

> **勘違い**: 特定のIPアドレスからのアクセスを Security Group で拒否できる。
> **実際は**: できません。Security Group には許可ルールしか書けず、「許可リストに載せない」ことが唯一の拒否手段です。

> **勘違い**: Security Group は Subnet に設定するものだ。
> **実際は**: リソース（正確には ENI）に紐付きます。同じ Subnet 内の EC2 でも別のルールを持てますし、Subnet をまたいで同じ Security Group を使い回すこともできます。

> **勘違い**: Route Table で経路を作ったのだから、通信は届くはずだ。
> **実際は**: Route Table は「どの道を通るか」、Security Group は「通してよいか」で、別のレイヤーです。両方が揃って初めて通信が成立します。

> **勘違い**: ソースには IPアドレスしか書けない。
> **実際は**: 別の Security Group の ID を指定できます。「app-sg が付いたリソースから」と書けるため、台数が変動してもルールを固定できます。

## この章で覚えるべきポイント

- [ ] Route Table（道が通っているか）と Security Group（通してよいか）は別レイヤーである
- [ ] Security Group は**ステートフル**で、許可した通信の戻りは自動的に通る
- [ ] Security Group には**許可ルールのみ**書ける。拒否ルールは存在しない
- [ ] Security Group は Subnet 単位ではなく**リソース（ENI）単位**で適用される
- [ ] ソースには CIDR のほか、別の Security Group ID を指定できる
- [ ] SSH（22番）のソースは `0.0.0.0/0` にせず、管理者のIPアドレスに限定する

### Solutions Architect Associate ではこう問われる

最頻出は **Security Group と Network ACL の区別**です。ステートフル／ステートレス、許可のみ／許可と拒否、リソース単位／Subnet 単位の3点セットで対比されます。本書では Network ACL を扱いませんが、この3点の違いは押さえておくと有利です。

次に多いのが**多層構成のソース指定**です。「Web サーバーからのみデータベースにアクセスさせたい」という要件には、RDS 側の Security Group のソースに EC2 側の Security Group ID を指定する選択肢が正解になります。CIDR でIPレンジを書く選択肢は、要件を満たしていても最適解として扱われないことが多いです。

「戻りの通信をアウトバウンドで許可する」という選択肢は、ステートフルの性質から誤りになります。この引っかけは頻出です。

# 第12章 CloudFront — 世界中にコピーを配る前線基地

> **この章でわかること**
> - S3に置いただけのファイルがなぜ遅くなりうるのかを説明できる
> - CDN・エッジロケーション・オリジン・キャッシュ・TTLといった用語を説明できる
> - CloudFrontとS3をOAC（Origin Access Control）でつなぐ推奨構成を説明できる
> - HTTPSがどこで終端されるか、独自ドメインの証明書がどこで必要になるかを説明できる
>
> **前の章とのつながり**: 前章で、Astroがビルドした `dist/` をS3という倉庫に置くところまで進みました。この章では、その倉庫にあるファイルを、世界中のユーザーにどう速く届けるかを見ていきます。

## なぜこれが必要なのか

前章でS3にファイルを置けば、そのファイルを配信すること自体はできます。しかし、S3のバケットは特定の1つの場所（リージョン）に存在します。たとえば東京リージョンにバケットを作った場合、ブラジルのユーザーがアクセスすると、リクエストとファイルのやり取りが地球の裏側との間で毎回発生し、表示までに時間がかかります。

また、アクセスが増えるたびに毎回S3から同じファイルを取り出すのは無駄が多く、S3への負荷も増えていきます。同じ内容のファイルを、世界中の利用者に近い場所から素早く配れる仕組みがあれば、この問題は解決できます。それを行うのがCloudFrontです。

## まずはざっくり: 中学生にもわかる説明

遠くの大きな倉庫（S3）から毎回商品を取り寄せていると、届くまでに時間がかかります。そこで、各地に小さな在庫拠点を作っておき、一度取り寄せた商品はそこに保管しておけば、次に近くの人が同じ商品を欲しがったときはすぐに渡せます。これが世界中の拠点から素早くファイルを届ける仕組み、CloudFrontの考え方です。

## 身近なたとえ

CloudFrontは「各地の前線倉庫・コンビニ」です。本部の大きな倉庫（S3）まで毎回買いに行くのではなく、近所のコンビニに商品が置いてあれば、そちらで受け取ったほうが早く済みます。CloudFrontは、世界中の拠点に一時的なコピーを置いておき、利用者に一番近い拠点から返答する役割を担います。

## 技術的にはこういうこと

**CloudFront**は、AWSが提供する**CDN（Content Delivery Network）**です。CDNとは、世界中に配置された拠点にコンテンツのコピーを保持し、利用者に地理的に近い拠点から配信することで、応答速度を向上させる仕組みを指します。

CDNの動きを理解するには、次の用語を押さえておく必要があります。

- **エッジロケーション**: CloudFrontがコンテンツのコピーを保持する、世界各地の拠点です。
- **オリジン**: CDNが配信する元データを持っている場所です。本書の構成ではS3バケットがオリジンにあたります。
- **キャッシュ**: 一度取得したデータを一時的に保存しておき、次回以降はそのコピーを使い回す仕組みです。
- **キャッシュヒット / キャッシュミス**: エッジロケーションに目的のファイルのコピーがあり、それを返せた場合を**キャッシュヒット**、コピーがなくオリジンまで取りに行く必要がある場合を**キャッシュミス**と呼びます。
- **TTL（Time To Live）**: キャッシュされたデータを、次にオリジンへ確認しに行くまで保持しておく有効期限のことです。
- **レイテンシー**: リクエストを送ってから応答が返るまでの遅延時間のことです。エッジロケーションが近いほど、一般にレイテンシーは小さくなります。

```text
        User (Browser)
              │
              ▼
        CloudFront   (Edge Location: cache hit)
              │
              ▼  cache miss only
            S3       (Origin)
```

エッジロケーションに目的のファイルのコピーがあればそのまま応答し（cache hit）、なければオリジンのS3まで取りに行きます（cache miss only）。

CloudFrontとS3の接続方法には、**OAC（Origin Access Control）**を使う方式と、古くから使われてきたOAI（Origin Access Identity）を使う方式や、S3の静的ウェブサイトホスティング機能を使ってバケットを直接公開する方式があります。本書ではOACを推奨構成とし、S3バケットは非公開のままにして、CloudFrontだけがそのバケットを読み取れるようにする構成を採用します。OAIやバケットの直接公開は旧来方式であり、新しく構成する場合はOACを使うのが基本です。

もう一つ重要な役割が、**HTTPSの終端**です。HTTPSとは、通信内容を暗号化してやり取りするための仕組みで、ブラウザとサーバーの間で第三者に通信内容を読み取られないようにします。この構成では、ユーザーとCloudFrontの間の通信をCloudFrontでHTTPSとして終端します。CloudFrontからS3へのアクセスは、OACによって署名されたリクエストとしてS3のHTTPSエンドポイントに送られるため、バケットを公開せずに安全に取得できます。独自ドメインでHTTPS通信を行うには証明書が必要になり、CloudFrontで使う証明書は**ACM（AWS Certificate Manager）**という別のサービスで発行します。ここで一点注意が必要なのは、CloudFront用のACM証明書は**us-east-1（バージニア北部）リージョンで発行する**必要があるという点です。証明書の詳しい扱いについては第17章で改めて触れます。

## AWSでの具体例

CloudFrontのディストリビューション（配信設定の単位）を作成する際は、主に次のような項目を設定します。

- オリジンとしてS3バケットを指定する
- オリジンアクセスとしてOACを設定し、S3バケットポリシーでCloudFrontからのアクセスのみを許可する
- デフォルトのキャッシュ動作（TTLなど）を設定する
- 独自ドメインを使う場合は、ACM（us-east-1）で発行した証明書を紐付ける

```text
        User (Browser)
              │
              ▼
         Route 53   (DNS: example.com ► CloudFront)
              │
              ▼
        CloudFront   (CDN / HTTPS / Cache)  ◄── 本章の主題
              │
              ▼
            S3       (dist/ : HTML, CSS, JS, images)
```

ファイルを更新して再度S3にアップロードしても、TTLの期間中はエッジロケーションに古いキャッシュが残ったままになることがあります。この場合、**キャッシュの無効化（Invalidation）**という操作を行い、古いキャッシュを明示的に破棄させる必要があります。

## フロントエンド開発との関係

NetlifyやVercelを使ってデプロイしたとき、実は皆さんのサイトもすでにCDN経由で配信されています。Netlify/Vercelにはそれぞれ独自のCDN（Vercel Edge Network、Netlify CDN）があり、ビルドが終わった瞬間にコンテンツが世界中の拠点へ配布され、さらに古いキャッシュのパージ（無効化）まで自動で行われます。

AWSでこの構成を自分で組む場合、CloudFrontの設定に加えて、デプロイのたびにキャッシュの無効化を自分で実行する必要があります。Netlify/Vercelがデプロイ完了時に自動でやってくれていたキャッシュのパージが、AWSでは明示的な作業として手元に戻ってくるということです。

## よくある勘違い

> **勘違い**: CloudFrontを使わなくても、S3にファイルを置けば十分速く配信できる
> **実際は**: S3は特定のリージョンに存在するため、遠方のユーザーにはレイテンシーが発生します。CloudFrontのエッジロケーションを経由することで、利用者に近い場所から配信できます。

> **勘違い**: S3バケットを公開設定にしてCloudFrontにつなぐのが標準的なやり方である
> **実際は**: 本書ではバケットを非公開にし、OACを使ってCloudFrontだけがアクセスできる構成を推奨します。バケットの直接公開は旧来方式です。

> **勘違い**: ファイルを更新してS3にアップロードすれば、すぐに新しい内容が世界中に反映される
> **実際は**: TTLの間はエッジロケーションに古いキャッシュが残ることがあります。すぐに反映したい場合はキャッシュの無効化（Invalidation）を行う必要があります。

> **勘違い**: 独自ドメインでHTTPSを使うための証明書は、CloudFrontを使うリージョンと同じ場所で発行すればよい
> **実際は**: CloudFront用のACM証明書は、必ずus-east-1（バージニア北部）で発行する必要があります。

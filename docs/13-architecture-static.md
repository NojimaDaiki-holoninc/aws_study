# 第13章 【組み立て1】Astro静的サイトのAWS構成

> **この章でわかること**
> - Astroなどでビルドした静的サイトをAWSで公開する構成を、Route 53・CloudFront・S3の3部品で説明できる
> - ブラウザにURLを入力してから画面が表示されるまでの流れを、キャッシュヒット時とミス時に分けて説明できる
> - この構成にVPC・EC2・ALB・RDSが登場しない理由を説明できる
> - `astro build` から公開までのデプロイ手順を、コマンドの並びとして説明できる
>
> **前の章とのつながり**: [第12章 CloudFront](./12-cloudfront.md)までで、静的サイトを配信するために必要な部品はすべて出そろいました。この章では新しい部品を足さず、これまでの部品を1本の構成につなぎ直します。

## なぜこれが必要なのか

部品を知っていることと、組み合わせて「動くWebサイト」にできることは別の能力です。Astroでビルドした `dist/` を公開したいとき、どの部品をどうつなげばよいのでしょうか。そして逆に、**どの部品は使わなくてよいのでしょうか**。この後者の判断が設計では一番効きます。VPCもEC2もALBもRDSもAWSの主要サービスですが、静的サイトを1本公開するだけならどれも必要ありません。

## まずはざっくり: 中学生にもわかる説明

やりたいことは単純です。「あらかじめ作っておいたファイルを、見たい人に渡す」。それだけです。Astroのようなツールがページをあらかじめ完成したHTMLにしてくれるので、訪問者が来てから計算する必要がありません。

必要なものは3つです。ファイルを**置いておく場所**、その**コピーを世界中に配っておく仕組み**（遠い人にも早く届けるため）、そして `example.com` という**名前を聞かれたときに行き先を答える案内役**です。

逆に言えば、計算するためのコンピューターも、それを守る土地も、データの保管庫も出てきません。計算しないのだから、計算する場所が要らないのです。

## 身近なたとえ

大量のパンフレットを配る場面です。原本一式は**巨大な倉庫**（S3）に保管しますが、注文のたびに本社倉庫から発送していては遠方の人に届くまで時間がかかります。そこで各地の**前線倉庫・コンビニ**（CloudFront）にあらかじめコピーを置きます。近所の店に在庫があればその場で受け取れ、切れていれば店が本社倉庫に取り寄せて次回のため手元にも1部残します。「あの店はどこか」と尋ねられて答えるのが**住所録**（Route 53）です。

この構成には**事務所**（EC2）も**敷地**（VPC）も**受付係**（ALB）も**金庫室**（RDS）も出てきません。働く人が要る仕事が1つもないからです。

## 技術的にはこういうこと

まず、この章の正本となる構成図を確認します。これは[はじめに](./00-introduction.md)で先に見せた図Aと同じものです。

```text
        User (Browser)
              │
              ▼
         Route 53   (DNS: example.com ► CloudFront)
              │
              ▼
        CloudFront   (CDN / HTTPS terminate / Cache)
              │
              ▼
            S3       (dist/ : HTML, CSS, JS, images)
```

この3段を、ブラウザがURLを受け取った瞬間から順に追います。

**ステップ1: 名前を住所に変える（Route 53）。**
ブラウザはまず「example.com のIPアドレスは何か」をDNS（ドメイン名とIPアドレスの対応表。[第3章](./03-ip-dns-domain.md)）に問い合わせ、最終的な答えを持つ権威DNSサーバーであるRoute 53（[第4章](./04-route53.md)）が応答します。ここで使うのが**Aliasレコード**です。`example.com` のようにサブドメインが付かない頂点（**Zone Apex**）にはDNSの仕様上CNAMEを置けないため、Aレコードの形でCloudFrontを直接指せるAliasを使います。

**ステップ2: 近くの前線基地に接続する（CloudFront）。**
返ってきたIPアドレスはCloudFront（[第12章](./12-cloudfront.md)）の**エッジロケーション**（世界各地の配信拠点）のもので、**ユーザーに地理的に近い拠点**が返されます。ブラウザとの間はHTTPSで暗号化され、それを解いてリクエストを取り出す**HTTPSの終端**をCloudFrontが担当します（独自ドメインで使うACM証明書はus-east-1での発行が必要です）。

**ステップ3: キャッシュがあるかを確認する。**
エッジロケーションは、要求されたファイルの写しを持っているかを確認します。持っていれば（**キャッシュヒット**）S3に問い合わせずその場で返すため、S3から見ればこのアクセスは存在しなかったのと同じです。持っていなければ（**キャッシュミス**）配信元である**オリジン**、すなわちS3に取りに行き、返すと同時に**TTL**（Time To Live。キャッシュを保持する秒数）の期間だけ手元にも保存します。次回はヒットになります。

**ステップ4: オリジンから取り出す（S3 + OAC）。**
キャッシュミスのときだけ、CloudFrontはS3（[第11章](./11-s3-ssg.md)）にリクエストを送ります。ここで重要なのが**OAC（Origin Access Control）**です。S3バケットは非公開のままにし、バケットポリシーで「このCloudFrontディストリビューションからのリクエストだけを許可する」と設定します。CloudFrontはOACで署名したリクエストを送るため非公開バケットから取得でき、入口はCloudFront1つに絞られます。

**この構成に登場しないもの。**
経路を最後まで追っても、VPC・Subnet・Internet Gateway・Route Table・NAT Gateway・Security Group・EC2・ALB・RDSが1つも出てきませんでした。S3もCloudFrontもRoute 53も**VPCの外側にあるサービス**だからです。VPC（[第5章](./05-vpc-subnet.md)）という「自分専用に借りた土地」が必要になるのは、EC2のような自分で管理するコンピューターを置く場合だけです。土地が要らないのだから、正門（[Internet Gateway](./06-igw-routetable.md)）もカーナビ（Route Table）も門番（[Security Group](./08-security-group.md)）も出番がありません。「EC2は動かす場所、S3は置く場所」という[第11章](./11-s3-ssg.md)の区別が、構成全体の形として現れています。

## AWSでの具体例

コンソールでの作業は次の順序になります。

1. **S3バケットを作成する。** パブリックアクセスはブロックしたままにし、静的ウェブサイトホスティングも有効にしません（OAC構成では不要です）。
2. **CloudFrontディストリビューションを作成する。** オリジンにそのS3バケットを指定し、オリジンアクセスに**OAC**を選択、案内されるバケットポリシーをS3側に適用します。
3. **ACM証明書をus-east-1で発行し**、代替ドメイン名（CNAMEs）に `example.com` を登録します。
4. **Route 53でAレコードを作成し、エイリアスを有効にして**CloudFrontディストリビューションを選びます。

次に、コードを更新して公開するまでのデプロイフローです。

```text
   Local / CI (GitHub Actions)
              │
              ▼ astro build
          dist/  (HTML, CSS, JS, images)
              │
              ▼ aws s3 sync dist/ s3://my-site-bucket
            S3
              │
              ▼ aws cloudfront create-invalidation
        CloudFront   (old cache purged)
              │
              ▼
        User sees new content
```

コマンドとしては次の3行です。

```bash
$ astro build
$ aws s3 sync dist/ s3://my-site-bucket --delete
$ aws cloudfront create-invalidation \
    --distribution-id E1XXXXXXXXXXXX --paths "/*"
```

1行目でHTMLを生成し、2行目で `dist/` をS3と同期します（`--delete` はローカルから消したファイルをS3側でも削除します）。3行目が**キャッシュの無効化（Invalidation）**です。S3を更新してもTTLの間はエッジに古い写しが残るため、明示的に破棄します。忘れると「デプロイしたのに古い画面が出る」状態になります。

## フロントエンド開発との関係

上の3行で気づくのは、**これがそのままCIのジョブになる**ことです。GitHub Actionsで `main` へのpushをトリガーにし、`npm ci` → `astro build` → `aws s3 sync` → `create-invalidation` を順に実行すれば、Netlifyで「pushしたら自動デプロイ」と呼んでいたものと同じ体験になります。つまりNetlifyやVercelの魔法の正体は、**この4ステップを自動で走らせてくれていた**ことです。AWSでは同じ4ステップを自分でワークフローファイルに書きます。Netlifyの管理画面の「ビルドコマンド」「publish directory」に相当する情報を、YAMLに書き下すだけです。

代わりに増える仕事もあります。CIからAWSを操作するための認証情報と権限の管理、そしてキャッシュ無効化の範囲の判断です。`--paths "/*"` で全消しするか変更ファイルだけを指定するかは自分で決めることになり、[第12章](./12-cloudfront.md)のTTL設計と一体の判断になります。

## よくある勘違い

> **勘違い**: 静的サイトでもVPCを作っておかないと、S3にファイルを置けない。
> **実際は**: S3・CloudFront・Route 53はいずれもVPCの外側のサービスです。VPCが必要になるのはEC2のような自分で管理するコンピューターを置く場合だけです。

> **勘違い**: CloudFrontを入れたので、すべてのアクセスがS3まで届いている。
> **実際は**: キャッシュヒットならエッジロケーションで応答が完結し、S3にはリクエストが届きません。オリジンの負荷が下がるのはこのためです。

> **勘違い**: CloudFrontを使うなら、S3バケットは公開設定にしておく必要がある。
> **実際は**: OACを使えばバケットは非公開のままにできます。ユーザーがS3のURLを直接叩いてもアクセスできません。

> **勘違い**: `aws s3 sync` でファイルを更新すれば、すぐに新しい画面が表示される。
> **実際は**: TTLの間はエッジロケーションに古い写しが残ります。すぐに反映したい場合は、Invalidationでキャッシュを明示的に破棄します。

## この章で覚えるべきポイント

- [ ] 静的サイトの構成は Route 53 → CloudFront → S3 の3段であり、EC2は登場しない
- [ ] Route 53からCloudFrontへはAliasレコードで向ける
- [ ] キャッシュヒットならS3には届かず、ミスのときだけオリジンのS3へ取りに行く
- [ ] S3バケットは非公開のままOACでCloudFrontからのみアクセスさせる
- [ ] デプロイは `astro build` → `aws s3 sync` → Invalidation の3ステップで、そのままCIに載る
- [ ] VPC・IGW・NAT Gateway・Security Group・ALB・RDSが不要なのは「動かす必要がない」から

### Solutions Architect Associate ではこう問われる

「静的なWebサイトを最小のコストと運用負荷で世界中に配信したい」という要件では、EC2やALBを含む選択肢を退けて**S3 + CloudFront**を選ばせる出題が定番です。「バケットを非公開に保ちたい」が加われば**OAC**が、「Zone Apexの独自ドメインを使いたい」が加われば**Aliasレコード**が決め手になります。CloudFront用ACM証明書のリージョン（us-east-1）も誤答を誘う条件としてよく登場します。

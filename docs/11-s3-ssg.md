# 第11章 S3とSSG — ファイルを「置く」場所

> **この章でわかること**
> - S3がオブジェクトストレージであり、EC2とは役割がまったく違うことを説明できる
> - バケット・オブジェクト・キーという基本用語を説明できる
> - AstroなどのSSG（静的サイトジェネレーター）でビルドした `dist/` をS3に配る流れを説明できる
> - なぜ静的サイトの配信にEC2が不要なのかを説明できる
>
> **前の章とのつながり**: 第10章までは、EC2でプログラムを動かし、RDSでデータを保管する「動くアプリケーション」のための部品を見てきました。この章からは視点を変え、Astroのようなツールで事前に作り終えたファイル一式をどう配るかという話に入ります。

## なぜこれが必要なのか

Astroで `npm run build` を実行すると、`dist/` フォルダの中にHTML・CSS・JavaScript・画像といった完成済みのファイルが出力されます。これらのファイルは、アクセスされるたびにサーバー側で何かを計算する必要がありません。ただ「そこにある」ものを、そのまま返せばよいだけです。

そうだとすると、わざわざEC2という「コンピューター」を借りて、Nginxのようなソフトウェアをインストールしてまで配信する必要はあるのでしょうか。プログラムを実行する仕組みは不要で、ファイルを保管して必要なときに取り出せる場所さえあれば十分なはずです。この「ファイルを置くだけの場所」を担当するのがS3です。

## まずはざっくり: 中学生にもわかる説明

S3は、インターネット上にある巨大な倉庫だと考えてください。段ボール箱（ファイル）を預けておくと、必要なときにその箱を取り出して誰かに渡すことができます。倉庫の管理人は、箱の中身を開けて何かを計算したりはしません。頼まれた箱をそのまま渡すだけです。

Astroでサイトを作ると、`dist/` フォルダの中に「もう完成した箱」が並びます。この箱をまるごとS3という倉庫に運び込んでおけば、あとは誰かがアクセスしてきたときに、その箱を取り出して渡すだけで済みます。

## 身近なたとえ

S3は「巨大な倉庫・ロッカー」です。EC2が「働く人がいる事務所（建物）」だったのに対し、S3は人が働く場所ではなく、ものを預けておくだけの倉庫です。事務所では従業員が注文を受けて何かを作りますが、倉庫では預けた荷物をそのまま出し入れするだけです。この違いが、EC2とS3の役割の違いそのものです。

## 技術的にはこういうこと

**S3（Simple Storage Service）**は、AWSが提供する**オブジェクトストレージ**です。オブジェクトストレージとは、ファイルをフォルダの階層構造ではなく「オブジェクト」という単位でフラットに保管する仕組みを指します。EC2のようにOSを起動してファイルシステムを操作するのではなく、ファイルそのものを直接預けたり取り出したりするサービスです。

S3には次の基本用語があります。

- **バケット（bucket）**: ファイルを入れる箱にあたる、S3上の保管場所の単位です。バケット名はAWS全体で一意である必要があります。
- **オブジェクト（object）**: バケットの中に保存される実体（ファイル本体とその付随情報）です。
- **キー（key）**: オブジェクトを一意に識別する名前です。`images/logo.png` のような文字列がキーになります。

ここで注意が必要なのは、S3には本来「フォルダ」という実体の階層構造がないという点です。管理画面上では `images/` フォルダの中に `logo.png` があるように見えますが、実際にはキー名に `/` が含まれているだけで、見かけ上フォルダのように表示されているにすぎません。

もう一つ重要な点は、**S3はVPCの中に置くサービスではない**ということです。第5章で見たVPCは「自分専用の土地」でしたが、S3は特定のVPCに属さず、VPCの外側にあるリージョン単位のサービスとして存在します。EC2やRDSのようにサブネットを指定して配置する対象ではありません。

```text
        Astro Project
              │
              ▼ astro build
           dist/           (HTML, CSS, JS, images)
              │
              ▼ upload
             S3            (bucket: my-site-bucket)
```

S3には**静的ウェブサイトホスティング**という、バケットに入れたファイルを直接Webサイトとして公開できる機能も存在します。ただし本書では、この機能を使ってバケットを直接公開するのではなく、バケットは非公開のままにし、次章で説明するCloudFrontを経由して配信する方針を取ります。理由は次章で説明します。

## AWSでの具体例

Astroでのビルドから配置までの流れは、おおむね次のようになります。

1. ローカルまたはCIで `astro build` を実行し、`dist/` フォルダを生成する
2. AWS CLIを使って `dist/` の中身をS3バケットへアップロードする

```bash
$ astro build
$ aws s3 sync dist/ s3://my-site-bucket
```

`aws s3 sync` は、ローカルの `dist/` フォルダの内容をS3バケットの中身と同期させるコマンドです。差分だけをアップロードするため、ビルドのたびにフォルダ全体を送り直す必要はありません。

バケットの設定画面では、バケットポリシー（誰がアクセスできるかのルール）やパブリックアクセスブロック（外部からの直接アクセスを一括で禁止する設定）といった項目があります。本書の方針では、バケットは非公開に設定し、外部からの直接アクセスはブロックしたままにします。

## フロントエンド開発との関係

NetlifyやVercelにデプロイするとき、皆さんは「publish directory」として `dist` を指定しているはずです。あの設定でNetlify/Vercelが裏側で行っているのは、まさにこの「ビルド済みファイルをストレージに配置する」処理です。Netlify/Vercelを使っていると、その保管場所がS3なのか別の仕組みなのかを意識する必要はありません。すべて自動で行われます。

AWSで同じことをする場合は、この「ビルド済みファイルをどこかに置く」という工程を自分でS3として明示的に用意し、アップロードのコマンドまで自分で実行する必要があります。裏側で当たり前に行われていた処理が、AWSでは自分の手で組み立てる部品の一つとして表に出てくるということです。

## よくある勘違い

> **勘違い**: S3はEC2の一種で、Webサーバーソフトウェアが動いている
> **実際は**: S3はプログラムを実行する場所ではなく、ファイルを保管するだけのオブジェクトストレージです。動的な処理は行われません。

> **勘違い**: S3の中はフォルダで階層的に整理されている
> **実際は**: 見た目はフォルダですが、実体はキー名に含まれる `/` によって階層があるように表示されているだけです。

> **勘違い**: 静的サイトを公開するにはS3の静的ウェブサイトホスティング機能を有効にすればよい
> **実際は**: その機能でも公開できますが、本書ではバケットを非公開にし、次章のCloudFrontを経由して配信する構成を採用します。

> **勘違い**: S3はVPCの中に配置するサービスである
> **実際は**: S3はVPCに属さない独立したサービスです。EC2やRDSのようにサブネットを指定して配置するものではありません。

## この章で覚えるべきポイント

- [ ] S3はオブジェクトストレージであり、EC2のようにプログラムを実行する場所ではないことを説明できる
- [ ] バケット・オブジェクト・キーの意味を説明できる
- [ ] S3上の「フォルダ」がキー名の `/` による見かけ上のものであることを説明できる
- [ ] S3がVPCの外にある独立したサービスであることを説明できる
- [ ] `astro build` で生成した `dist/` をS3へアップロードする流れを説明できる

### Solutions Architect Associate ではこう問われる

S3は「オブジェクトストレージ」であり、ブロックストレージ（EBS）やファイルストレージ（EFS）と区別されて出題されます。「大量の静的ファイルを安価かつ高い耐久性で保管したい」という状況ではS3が正解になりやすい一方、「OSからマウントして使うディスク」が求められる場面ではEBSが正解になります。また、S3バケットを非公開にしたままCloudFront経由でのみアクセスさせる構成（OAC。Origin Access Control。次章で説明する、S3を非公開のままCloudFrontだけに読み取りを許可する仕組み）は頻出パターンです。バケットを直接パブリックにする静的ウェブサイトホスティングは、要件で明示されない限り推奨される構成ではない点も意識しておくとよいでしょう。

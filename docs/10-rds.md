# 第10章 RDS — データを預かる金庫

> **この章でわかること**
> - EC2にデータベースを同居させると何が困るのかを説明できる
> - RDSが「マネージドサービス」であるとはどういうことかを説明できる
> - RDSをどこに配置し、どんな通信だけを許可するかを説明できる
>
> **前の章とのつながり**: 第9章でEC2は複数台に増え、Private Subnetへ移りました。複数台のEC2が同時に動く以上、データはどこか1台のEC2の中ではなく、共有できる場所に置く必要があります。

## なぜこれが必要なのか

もしデータベースを1台のEC2の中に同居させていたらどうなるでしょうか。まず、第9章でEC2を複数台に増やしてAuto Scalingで自動増減させるようになると、どのEC2が「本物のデータ」を持っているのかが曖昧になります。あるEC2に書き込んだデータが、別のEC2からは見えないという不整合が起きてしまいます。さらに、Auto Scalingによって不要になったEC2が終了（削除）されるとき、そのEC2の中にデータがあれば、それも一緒に消えてしまいます。つまり、「複数台で共有できて、EC2の増減とは独立して存在し続けるデータの置き場所」が必要です。

## まずはざっくり: 中学生にもわかる説明

お店のスタッフを増やしたり減らしたりするようになったとき、売上の記録を特定のスタッフの手帳にメモしていたら、そのスタッフが辞めた瞬間に記録も失われてしまいます。そこで、記録は建物の奥にある専用の金庫室にまとめて保管し、どのスタッフもその金庫室を見に行けばよい、という形にします。スタッフの人数がどう変わっても、金庫室の中身は影響を受けません。RDSはこの金庫室にあたります。

## 身近なたとえ

RDS（Relational Database Service）は「金庫室・書庫」です。敷地（VPC）の奥の区画（Private Subnet）に置かれ、事務所（EC2）で働くスタッフたちが必要なときに出し入れします。この金庫室には専門の管理人がついていて、書類の補修や複製、緊急時の復旧といった作業を代行してくれます。この「専門の管理人がついている」という部分が、後で説明する「マネージド」の意味に対応します。

## 技術的にはこういうこと

RDS（Relational Database Service）は、MySQLやPostgreSQLといったリレーショナルデータベースをAWS上で運用するための**マネージドサービス**です。マネージドサービスとは、利用者が自分でサーバーにデータベースソフトをインストールして運用する代わりに、OSやミドルウェアのセットアップ・パッチ適用・バックアップ取得・障害発生時の復旧といった運用作業の多くをAWS側が代行してくれるサービスの形態を指します。EC2上に自分でMySQLを入れて運用することもできますが、その場合はセキュリティパッチの適用やバックアップの取得、障害時の切り分けまですべて自分で行う必要があります。RDSではこれらの多くをAWSに任せられます。

RDSは、第9章までの構成と同様にPrivate Subnetに置きます。直接さらされてはいけない情報を扱うため、インターネットから直接アクセスされない場所に置くのが原則です。RDSへのアクセスは、EC2のSecurity Group（門番）からの通信のみに限定します。送信元にIPアドレスの範囲ではなく「EC2のSecurity Group」そのものを指定できる点が、EC2同士の通信を許可する際によく使われる方法です。

RDSを配置する際には、**DBサブネットグループ**という設定が必要です。これはRDSインスタンスをどのSubnet群に配置してよいかを定義するもので、**2つ以上のAZにまたがるSubnetを含める必要があります**。これは第9章で説明したALBのマルチAZ要件と同じ理由で、1つのAZが利用できなくなった場合に備えるためです。ただし、本章で扱う構成自体は1つのRDSインスタンスを前提とした簡略図であり、実際に複数AZで自動的に待機系を用意する仕組みは「Multi-AZ」という機能によって実現されます。Multi-AZの詳細は第17章で扱いますが、ここでは「同一AZに障害が起きてもデータベースを継続利用できるようにする仕組みが別途存在する」という名前だけ押さえておいてください。

```text
            Internet
               │
               ▼
      ┌─── Internet Gateway ───┐
      │                        │
┌─────┴────────── VPC ─────────┴─────┐
│ 10.0.0.0/16                        │
│                                    │
│  ┌─── Public Subnet 10.0.1.0/24 ─┐ │
│  │   ALB                         │ │
│  │   NAT Gateway                 │ │
│  └───────────────────────────────┘ │
│                 │                  │
│                 ▼                  │
│  ┌─── Private Subnet 10.0.2.0/24 ┐ │
│  │   EC2  (App / Auto Scaling)   │ │
│  │   RDS  (Database)             │ │  ◄── ここが本章の主題
│  └───────────────────────────────┘ │
│                                    │
└────────────────────────────────────┘
```

RDSはPrivate Subnetに置かれ、DBサブネットグループは2つ以上のAZにまたがるSubnetで構成する必要があります（本図は簡略図）。

```text
       EC2 (Security Group: app-sg)
              │  3306 (MySQL) / 5432 (PostgreSQL)
              ▼
       RDS  (Security Group: db-sg)
              allow: source = app-sg only
```

送信元はEC2のSecurity Group（app-sg）、許可ポートはMySQLなら3306番、PostgreSQLなら5432番です。

## AWSでの具体例

実際にAWSでRDSを構成する場合は、次のような設定を行います。

- **DBサブネットグループ**を作成し、Private Subnetのうち2つ以上のAZにまたがるSubnetを登録する。
- RDSインスタンス作成時に、使用するデータベースエンジン（MySQL、PostgreSQLなど）とインスタンスクラス（性能・スペック）を選択する。
- RDS用のSecurity Groupを作成し、インバウンドルールの送信元にEC2側のSecurity Group（例: `app-sg`）を指定し、ポートをデータベースエンジンに応じたもの（3306番や5432番）に設定する。
- 自動バックアップの保持期間やバックアップウィンドウ（バックアップを取得する時間帯）を設定する。これらの取得作業自体はAWSが自動で行う。
- 接続先のエンドポイント（RDSに割り当てられるホスト名）をEC2側のアプリケーション設定に渡し、EC2からRDSへ接続できるようにする。

## フロントエンド開発との関係

Supabase、PlanetScale、Vercel PostgresといったサービスをNext.jsなどのプロジェクトで使ったことがある方は、それらの体験に近いものがRDSです。これらのサービスも「データベースソフトのインストールやパッチ適用を意識せず、接続情報だけ受け取ってすぐ使える」という点でマネージドサービスの一種です。違いは、Supabaseなどがネットワーク構成まで含めて隠蔽してくれているのに対し、RDSではVPC・Subnet・Security Groupというネットワークの置き場所を自分で設計する必要がある点です。「マネージドである」という利便性は共通していますが、AWSではそれを自分の敷地の中の一部として組み込む作業が追加で発生します。

## よくある勘違い

> **勘違い**: RDSを使えば、パッチ適用やバックアップを何も考えなくてよい。
> **実際は**: OSやミドルウェアの管理はAWSが代行しますが、バックアップの保持期間設定やスケーリングの判断など、利用者側で決めるべき設定は残ります。「何もしなくていい」わけではなく「運用の一部を肩代わりしてもらえる」という意味です。

> **勘違い**: RDSもEC2と同様にPublic Subnetに置いてもよい。
> **実際は**: RDSは重要なデータを扱うため、原則としてPrivate Subnetに置き、インターネットから直接アクセスできないようにします。

> **勘違い**: RDSへのアクセス許可は、EC2のIPアドレスを直接指定する必要がある。DBサブネットグループも1つのSubnetだけで構成できる。
> **実際は**: 送信元にはEC2のSecurity Groupそのものを指定でき、IPアドレスが変わっても設定変更が不要です。またDBサブネットグループには2つ以上のAZにまたがるSubnetを含める必要があります。

> **勘違い**: RDSを使えば自動的にMulti-AZになり、障害時も無停止で切り替わる。
> **実際は**: 複数AZでの待機系構成は「Multi-AZ」という別途有効化する機能です。RDSを使うだけで自動的に有効になるわけではありません（詳細は第17章）。

## この章で覚えるべきポイント

- [ ] RDSはマネージドなリレーショナルデータベースサービスであり、パッチ適用・バックアップ・障害復旧の多くをAWSが代行する
- [ ] EC2にデータベースを同居させると、複数台構成でのデータ不整合やEC2削除時のデータ消失が起きる
- [ ] RDSはPrivate Subnetに置き、EC2のSecurity Groupからの3306番/5432番のみを許可する
- [ ] DBサブネットグループは2つ以上のAZにまたがるSubnetが必要である
- [ ] Multi-AZは名前だけ押さえ、詳細は第17章で学ぶ

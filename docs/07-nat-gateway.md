# 第7章 NAT Gateway — 中から外へだけ出る通用口

> **この章でわかること**
> - Private Subnet に置いたサーバーが「外に出られない」と何が困るのかを説明できる
> - NAT Gateway が Public Subnet に置かれる理由と、通信がどの順に流れるかを説明できる
> - NAT（Network Address Translation）が何を書き換えているのか、なぜ外から入れないのかを説明できる
> - NAT Gateway に Elastic IP が必要な理由と、コストが発生する要素を説明できる
>
> **前の章とのつながり**: 第6章で「Public Subnet とは、`0.0.0.0/0` が Internet Gateway を向く Route Table が関連付けられた Subnet のことだ」と定義しました。この章では、その Route Table を持たない Private Subnet 側の話に進みます。

## なぜこれが必要なのか

Private Subnet は「インターネットから直接アクセスされない区画」でした。データベースや内部APIのように、外から触られては困るものを置く場所です。ではそのサーバーは、OSのセキュリティアップデートや `npm install` のパッケージを、どうやって取得するのでしょうか。外部APIの呼び出しも含め、どれもサーバーの側から外へ出ていく通信です。

外から入られたくはない。しかし中から外へは出たい。第6章の Internet Gateway を Private Subnet の Route Table に設定すれば外へは出られますが、それをした瞬間その Subnet は定義上 Public Subnet になり、「外から直接アクセスされない」という性質を失います。

この「出るのは許可、入るのは拒否」という非対称な通信を実現する仕組みが NAT Gateway です。

## まずはざっくり: 中学生にもわかる説明

建物には、玄関のように両方向に通れる出入口のほかに、非常口や店の裏の搬入口のように「中からは押せば開くけれど、外側にはノブがない」扉があります。Private Subnet に置いたサーバーがほしいのは、この後者の扉です。

NAT Gateway は、その「中からしか開かない扉」をネットワークの世界で作る仕組みです。扉は敷地の表側（Public Subnet）に設置されるので、奥の区画にいる人はいったん表まで出てきてから外に出る流れになります。

## 身近なたとえ

NAT Gateway は**通用口**です。

わかりやすいのは出前を頼むときです。奥の区画にいる人が外の店に注文しますが、奥に配達員は入れたくありません。そこで注文は通用口を経由して外へ出し、届いた弁当も通用口で受け取って本人のところへ運びます。外の店から見えているのは通用口だけです。

そして、注文していない配達員が突然通用口から入ってくることはできません。通用口が通すのは**こちらが出した注文に対する返事**だけで、この性質が NAT Gateway の一番大事な部分です。

## 技術的にはこういうこと

**NAT Gateway** は、Private Subnet 内のリソースがインターネットへ向けて発信する通信を中継し、その戻りの通信だけを内側へ返す AWS のマネージドサービスです。マネージドサービスとは、サーバーの用意・冗長化・パッチ適用といった運用作業を AWS 側が担当してくれるサービスを指します。

**NAT は何を変換しているのか。** NAT は **Network Address Translation**（ネットワークアドレス変換）の略で、パケットに書かれた**送信元のIPアドレスを書き換える**仕組みです。第5章で見たとおり `10.0.2.0/24` のようなプライベートIPアドレスはインターネット上では使えません（世界中で重複しており、返事の宛先として成立しない）。そこで NAT Gateway は、届いたパケットの送信元を自分が持つパブリックIPアドレスに書き換えてから送り出します。

```text
  Server (10.0.2.10)      NAT Gateway (Public IP)      Internet

  (1) request : outbound
        │  src=10.0.2.10        │  src=<Public IP>        │
        ├──────────────────────►├────────────────────────►│

  (2) reply : inbound  (flows right to left)
        │  dst=10.0.2.10        │  dst=<Public IP>        │
        │◄──────────────────────┤◄────────────────────────┤

  (3) new connection from outside
        │                       │◄────────────────────────┤
        │      (X) dropped : no matching entry            │
```

（凡例）(1) は中から外への通信で、送信元IPが `10.0.2.10` からパブリックIPへ書き換えられ
ます。(2) はその戻りで、右から左へ流れ、宛先IPがパブリックIPから `10.0.2.10` へ戻されま
す。(1) と (2) は矢印の向きが逆なので、変換されるアドレスも送信元と宛先で入れ替わります。
(3) は外部から NAT Gateway へ直接来る新規接続で、対応表に記録がないため NAT Gateway の
手前で破棄され、内側には届きません。

NAT Gateway は「どの内部アドレスの、どの**ポート**（1台のコンピューター上で複数の通信を区別する番号）から出た通信か」を対応表として記憶しています。戻りのパケットが届くと、この対応表を引いて元のサーバーへ転送します。

**なぜ外から入れないのか。** インターネット側から NAT Gateway のパブリックIP宛にいきなりパケットが届いても、それが `10.0.2.10` 宛なのか `10.0.2.20` 宛なのかを判断する材料がありません。つまり「拒否する設定をしている」のではなく、**仕組みとして外部からの新規接続を成立させられない**のです。

**配置と経路。** ここが最も間違えやすい点です。**NAT Gateway は Public Subnet に置きます。** NAT Gateway 自身がインターネットへ出ていく必要があり、そのためには `0.0.0.0/0` が Internet Gateway を向く Route Table、すなわち Public Subnet に所属していなければならないからです。

```text
            Internet
               │
               ▼
      ┌─── Internet Gateway ───┐        ▲ (3) IGW ► Internet
      │                        │
┌─────┴────────── VPC ─────────┴─────┐
│ 10.0.0.0/16                        │
│                                    │
│  ┌─── Public Subnet 10.0.1.0/24 ─┐ │
│  │   NAT Gateway (Elastic IP)    │ │  ◄── ここが本章の主題
│  │   EC2 (Web)                   │ │
│  └───────────────────────────────┘ │
│                 ▲                  │  ▲ (2) Private ► NAT GW
│                 │                  │
│  ┌─── Private Subnet 10.0.2.0/24 ┐ │
│  │   Server (App / RDS)          │ │  ▲ (1) outbound start
│  └───────────────────────────────┘ │
│                                    │
└────────────────────────────────────┘
```

（凡例）(1) Private Subnet のサーバーが外向きに発信 → (2) Private Subnet の Route Table
により NAT Gateway へ → (3) Public Subnet の Route Table により IGW からインターネットへ。
戻りは同じ経路を逆向きにたどります。

なお第5〜8章では説明を単純にするため EC2 を Public Subnet に置いています。上の図で Private Subnet に描いているのは、第9章で EC2 を移す先、あるいは第10章で扱う RDS のようなリソースだと考えてください。

**Elastic IP とコスト。** NAT Gateway の作成には **Elastic IP** の割り当てが必須です。Elastic IP とは、AWS が払い出す固定のパブリックIPアドレスで、明示的に解放しない限り変わらないものを指します。送信元アドレスとして書き換える先が決まっていなければ変換ができないため、省略できません。

また NAT Gateway は無料ではなく、**起動している時間に対する課金**と、**通過したデータ量に対する処理課金**の2つがかかります。金額は変動するため書きませんが、置いておくだけで課金が続く点は覚えておいてください。

## AWSでの具体例

**1. NAT Gateway を作成する。** VPC の画面で「NAT ゲートウェイ」を作成し、Subnet に `10.0.1.0/24`（**Public Subnet を選ぶ**）、Connectivity type に `Public` を指定し、「Elastic IP を割り当て」で新規に割り当てます。作成されると `nat-0a1b2c3d...` のようなIDが振られます。

**2. Private Subnet の Route Table にデフォルトルートを追加する。** Private Subnet に関連付けられた Route Table を次の状態にします（`local` の行は VPC 作成時からある内部通信用の経路なので、追加するのは2行目だけです）。

| Destination | Target |
|---|---|
| `10.0.0.0/16` | `local` |
| `0.0.0.0/0` | `nat-0a1b2c3d...` |

**3. Public Subnet 側の Route Table は変更しない。** 第6章の時点ですでに `0.0.0.0/0 → igw-0a1b2c3d...` が入っているはずで、NAT Gateway はこの経路に相乗りして外へ出ます。

つまり Route Table が2種類（Public 用と Private 用）必要になります。第6章までは1種類で足りていましたが、この章から使い分けが始まります。

## フロントエンド開発との関係

Netlify や Vercel にリポジトリを繋いでデプロイすると、ビルドサーバー上で `npm install` が走り、npm レジストリという外部のサーバーへ通信します。**外から入られる必要はまったくないが、外へ出る必要は必ずある**という、この章とまったく同じ構図です。

そのビルドサーバーに外部から SSH でログインすることはできませんが、それでも `npm install` は成功します。プラットフォーム側が「出ていく通信だけを通す」経路を用意しているからで、AWS でそれを自分で組むと NAT Gateway になる、という関係です。Next.js の Route Handlers から外部APIを叩く場合も同じで、Vercel では意識しなくても通っていた外向き通信が、AWS では「部品を1つ足して経路を作る作業」として顔を出します。

## よくある勘違い

> **勘違い**: NAT Gateway は Private Subnet に置く。
> **実際は**: Public Subnet に置きます。NAT Gateway 自身が `0.0.0.0/0 → igw-xxxx` の Route Table を使って外へ出る必要があるためです。

> **勘違い**: NAT Gateway を置くと、Private Subnet のサーバーに外部からアクセスできるようになってしまう。
> **実際は**: できません。外部から届いた新規の接続は対応表に記録がなく、どこへ転送すべきか判断できないため破棄されます。

> **勘違い**: NAT Gateway があれば Internet Gateway は不要になる。
> **実際は**: 両方必要です。NAT Gateway は中継役に過ぎず、VPC とインターネットの境界を担うのは Internet Gateway です。

> **勘違い**: NAT Gateway を作れば通信が通るようになる。
> **実際は**: Private Subnet の Route Table に `0.0.0.0/0 → nat-xxxx` を追加して初めて経路が成立します。設置と経路設定は別作業です。

> **勘違い**: NAT Gateway は無料で置いておける。
> **実際は**: 起動時間に対する課金と、通過データ量に対する処理課金がかかります。学習用の VPC では使い終わったら削除してください。

## この章で覚えるべきポイント

- [ ] Private Subnet のサーバーも、OSアップデートや `npm install` のために「外へ出る」必要がある
- [ ] NAT Gateway は **Public Subnet** に置き、Elastic IP の割り当てが必須である
- [ ] Private Subnet の Route Table で `0.0.0.0/0 → nat-xxxx` を設定して初めて経路が通る
- [ ] NAT は Network Address Translation の略で、送信元IPアドレスを書き換えている
- [ ] 外から入れないのは、対応表にない通信の転送先が判断できないためである
- [ ] NAT Gateway には時間課金とデータ処理課金があり、放置すると費用が発生し続ける

### Solutions Architect Associate ではこう問われる

まず問われるのは配置です。「Private Subnet の EC2 がインターネット上のリポジトリにアクセスできない」状況で、NAT Gateway が Private Subnet に置かれている、あるいは Route Table の設定が抜けている、という原因を選ばせる形式が典型です。**NAT Gateway は Public Subnet、Elastic IP 必須**をセットで覚えてください。

次に Internet Gateway との役割の違いです。「外部から接続を受ける必要はなく、外向き通信だけ許可したい」という要件なら NAT Gateway が正解です。逆に「インターネットから直接アクセスさせたい」なら Public Subnet と Internet Gateway になります。

もう1つ、NAT インスタンス（EC2 に自分で NAT を構成する旧来の方式）との対比もあります。可用性（システムが停止せずに使える度合い）と運用負荷の観点からは、AWS が管理する NAT Gateway が推奨される選択肢です。

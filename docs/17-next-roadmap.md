# 第17章 次に学ぶことのロードマップ

> **この章でわかること**
> - 本書の次に学ぶべき項目を、理解が積み上がる順番で把握できる
> - 各項目が本書のどの章の続きにあたるかを説明できる
> - それぞれを学ぶと何がわかるようになるかを、事前に把握できる
>
> **前の章とのつながり**: 第16章で全体図を1枚にまとめました。この章では、その図にまだ描かれていない部品を、どの順番で足していくかを示します。

本書で扱った部品だけでも、静的サイトとサーバーアプリの構成は組めます。しかし実務で運用するには、まだ足りないものがあります。それらを片端から学ぼうとすると、前提知識が足りずに何度も戻ることになります。ここでは、**前の項目が次の項目の土台になる順番**を示します。

## 1. IAM

**なぜこの順番か**: IAM（Identity and Access Management）は、AWSにおける「誰が何をしてよいか」を定義する仕組みです。EC2を起動する、S3にファイルを置く、RDSに接続する。本書で行ったすべての操作は、実はIAMの権限があって初めて成立しています。ここを飛ばすと、この先どのサービスを学んでも「なぜか権限エラーで動かない」という壁に当たり続けます。

**何がわかるようになるか**: ユーザー・グループ・ロール・ポリシーの違いと、必要最小限の権限だけを与える考え方がわかります。特に**IAMロール**は重要で、EC2がS3にアクセスするときにアクセスキーをサーバーに置かずに済む仕組みです。第11章でS3にアップロードした `aws s3 sync` が、なぜ認証情報を必要としたのかもここで腑に落ちます。

**SAAではどう関わるか**: 「EC2からS3にアクセスさせたい」という要件でIAMロールを選ばせる設問が定番です。

## 2. Availability Zone / Multi-AZ

**本書のどの章の続きか**: 第5章（Subnetは1つのAZに属する）、第9章（ALBは2AZ以上必要）、第10章（DBサブネットグループは2AZ以上必要）で名前だけ触れた内容の完成形です。

**なぜこの順番か**: 本書では「2AZ以上必要」という事実だけを述べ、理由を先送りしてきました。AZ（Availability Zone）とは、1つのリージョンの中にある、電源・空調・ネットワークが独立した複数のデータセンター群のことです。これを理解して初めて、なぜ複数AZが可用性の前提なのかが説明できるようになります。

**何がわかるようになるか**: リージョンとAZの関係、AZ障害という事象、そしてRDSの**Multi-AZ**（別AZに待機系を自動で用意し、障害時に自動で切り替える機能）が何をしてくれるのかがわかります。Multi-AZは可用性を上げる機能であり、読み取り性能を上げるRead Replicaとは目的が違う、という区別もここで身に付きます。

**SAAではどう関わるか**: 可用性を問う設問のほぼすべてがAZの理解を前提にしています。最頻出領域です。

## 3. ACM

**本書のどの章の続きか**: 第12章で「CloudFront用の証明書はus-east-1で発行する」とだけ書いた、その証明書そのものの話です。

**なぜこの順番か**: HTTPSは本書ですでに登場しており、証明書だけが宙に浮いた状態になっています。ここを埋めておくと、独自ドメインでHTTPSを有効にする作業を最後まで自力で完結できるようになります。

**何がわかるようになるか**: ACM（AWS Certificate Manager）で証明書を無料で発行し、自動更新させる流れがわかります。DNS検証（Route 53にレコードを1つ追加してドメインの所有を証明する方法）と、証明書を発行するリージョンの制約（CloudFrontならus-east-1、ALBならALBと同じリージョン）が理解できます。

**SAAではどう関わるか**: 「証明書をどのリージョンで発行するか」を問う設問が典型です。

## 4. CloudWatch

**なぜこの順番か**: ここまでで「構成を作る」ことはできますが、「作ったものが今どうなっているか」を見る手段がありません。次に進む前に、動いているものを観測できる状態を作っておくべきです。第9章のAuto Scalingが「CPU使用率に応じて」台数を増やすと説明しましたが、そのCPU使用率を測っているのがCloudWatchです。

**何がわかるようになるか**: メトリクス（数値の時系列データ）、ログ、アラーム（閾値を超えたら通知する仕組み）の3つの役割がわかります。Auto Scalingのスケーリングポリシーが何を見て発動しているのか、EC2上のアプリケーションのエラーログをどこに集めるのかが、具体的な設定として理解できるようになります。

**SAAではどう関わるか**: Auto Scalingや通知の設問で、CloudWatchアラームを起点とする構成が正解になります。

## 5. AWS料金体系

**なぜこの順番か**: ここから先は「同じ目的を達成する複数の方法」を比較する話になります。その比較にはコストという軸が不可欠です。第7章でNAT Gatewayに時間課金とデータ処理課金があると触れましたが、あのような「置いておくだけでかかる費用」の全体像を先に押さえておくと、6以降の選択肢を正しく評価できます。

**何がわかるようになるか**: 課金の主な軸（起動時間、データ転送量、リクエスト数、確保しているだけでかかる料金）と、EC2の購入オプション（オンデマンド、リザーブドインスタンス、Savings Plans、スポットインスタンス）の使い分けがわかります。「なぜ静的サイトはCloudFront + S3のほうが安いのか」を数字の構造として説明できるようになります。

**SAAではどう関わるか**: 「最もコスト効率の高い構成はどれか」という問い方が非常に多く、可用性と並ぶ2大評価軸です。

## 6. Lambda / API Gateway

**本書のどの章の続きか**: 第2章で「EC2はプログラムを動かす場所」と定義しました。その「動かす場所」の、まったく別の選択肢です。

**なぜこの順番か**: EC2という基準を持っている今だからこそ、Lambdaの「サーバーを持たない」という特徴の意味がわかります。逆順で学ぶと、何が省略されているのかが見えません。

**何がわかるようになるか**: Lambdaは、コードを登録しておくとリクエストが来たときだけ実行される仕組みです。EC2のように常時起動している必要がないため、アクセスがない時間帯の費用が発生しません。API Gatewayは、そのLambdaをHTTPのエンドポイントとして公開する部品で、サーバーアプリ構成におけるALBの位置に相当します。この2つを学ぶと、**VercelのAPI RoutesやServer Actionsが裏で何をしているのか**が、AWSの部品として説明できるようになります。

**SAAではどう関わるか**: 「常時稼働が不要な処理」「イベント駆動の処理」ではLambdaが正解になりやすい形です。

## 7. ECS / Fargate

**本書のどの章の続きか**: 第2章のEC2と、6のLambdaの中間にあたる選択肢です。

**なぜこの順番か**: 両端（EC2とLambda）を知ってから中間を学ぶほうが、位置づけを理解しやすいためです。

**何がわかるようになるか**: コンテナ（アプリケーションと実行環境をひとまとめにした単位）をAWSで動かす方法がわかります。ECS（Elastic Container Service）がコンテナの起動・停止・台数を管理する仕組みで、Fargateはそのコンテナを動かすサーバーをAWS側が用意してくれる方式です。Fargateを使うと、EC2インスタンスのOS管理から解放されつつ、Lambdaのような実行時間の制約は受けずに済みます。第9章のAuto Scalingが「EC2の台数」だったのに対し、ECSでは「コンテナの数」を同じ発想で管理することになります。

**SAAではどう関わるか**: 「コンテナを動かしたいがサーバー管理はしたくない」ならFargateが正解になります。

## 8. Secrets Manager

**本書のどの章の続きか**: 第10章でRDSに接続する際、エンドポイントとユーザー名・パスワードをEC2側のアプリケーションに渡す、と書きました。その「渡し方」の正解にあたる部分です。

**なぜこの順番か**: IAM（1）を理解していないと、Secrets Managerの「誰がこの秘密を読めるか」という核心部分が理解できません。だからIAMの後に置いています。

**何がわかるようになるか**: データベースのパスワードやAPIキーを、コードや環境変数に直接書かずに管理する方法がわかります。Secrets Managerはこれらを暗号化して保管し、IAMロールを持つリソースだけが実行時に取り出せるようにする仕組みです。パスワードの自動ローテーション（定期的な自動変更）にも対応しています。VercelのEnvironment Variablesに相当するものを、AWSではどう実現するかという話でもあります。

**SAAではどう関わるか**: 「認証情報をコードに埋め込まない」という要件で、Secrets ManagerまたはParameter Storeが正解になります。

## 9. Infrastructure as Code の考え方 → CloudFormation → CDK → Terraform

**本書のどの章の続きか**: 第5章から第9章まで、VPCを作り、Subnetを2つ作り、Route Tableを作って関連付け、Security Groupを設定しました。あれを**すべてコードとして書く**、というのがこの項目です。

**なぜこの順番か**: 最後に置いているのは、書く対象を知らないとコードも書けないからです。手作業で一度組んだ経験があって初めて、コードにする意味（同じ構成を再現できる、変更履歴が残る、レビューできる、環境を丸ごと作り直せる）が実感を伴って理解できます。

**何がわかるようになるか**: まず**Infrastructure as Code（IaC）の考え方**そのものを押さえます。インフラの構成をコードとして記述し、そのコードを実行することで実際のリソースを作る、という発想です。フロントエンドで `package.json` があれば同じ依存関係を再現できるのと同じ考え方を、インフラに適用したものだと考えてください。

次に具体的なツールを、この順で見ていきます。

- **CloudFormation**: AWSが公式に提供するIaCサービスです。YAMLまたはJSONでリソースを記述します。まずこれを見ると、IaCが「宣言的に書いた状態にAWSを合わせる」仕組みであることがわかります。
- **CDK（Cloud Development Kit）**: CloudFormationのテンプレートを、TypeScriptなどのプログラミング言語で生成できるツールです。フロントエンドエンジニアにとっては最も入りやすい選択肢で、型補完を効かせながらVPCやALBを定義できます。CloudFormationを先に見ておくと、CDKが最終的に何を出力しているのかがわかるため、エラーの原因を追えるようになります。
- **Terraform**: HashiCorp社が提供する、AWS以外のクラウドサービスにも対応したIaCツールです。複数のクラウドやSaaSをまとめて管理したい場合の選択肢になります。AWS専用のCloudFormation / CDKとの違いを理解した上で選べるように、最後に置いています。

**SAAではどう関わるか**: 「同じ構成を複数の環境に再現したい」という要件でCloudFormationが正解になります（TerraformやCDKは試験の主対象ではありませんが、実務では選択肢に入ります）。

## 最後に

ここまで読み進めた方は、AWSのサービス名を17章分覚えたわけではありません。覚えたのは、**Webサービスがどんな部品でできていて、その部品同士がどうつながっているか**です。ドメイン名を住所に変換する部品があり、その先に配信を速くする部品があり、あるいはリクエストを振り分ける部品があり、その奥にプログラムを動かす部品とデータを預かる部品がある。それらを囲む土地があり、外とつなぐ門があり、道を示す標識があり、入口に門番が立っている。この章で挙げた14項目も、そしてこの先AWSに追加される新しいサービスも、すべてこの図のどこかに置かれる部品です。新しいサービス名を見たときに「これは全体図のどこに入るのか」「どの部品の代わりになるのか」と問える限り、学ぶべきことはもう暗記ではありません。AWSとは、大量のサービス名を覚えるものではなく、Webサービスを構成する部品と、その部品同士の関係を理解するものです。
